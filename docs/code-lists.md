# Hosted code lists

How Meridian hosts a code list, and what the next one reuses. `usitc/hts` (the Harmonized Tariff Schedule of the United States) and `census/schedule_b` (the Census Bureau's export codes) were the first two, `cms/hcpcs` (HCPCS Level II, CMS's billing codes) the third, and `fda/ndc` (the FDA's National Drug Code directory) the fourth. The two Standard Occupational Classifications, `bls/soc_2018` (the US 2018 SOC, from the Bureau of Labor Statistics) and `ons/soc_2020` (the UK's SOC 2020, from the Office for National Statistics), were the first datasets published by their own Protocol's publish step, into the open lake (see [`docs/publishing.md`](publishing.md)); each comes with a job-title index and an edition crosswalk, written by the same Protocol, and they are the first lists to carry those two tables. `census/fips` (the Census Bureau's FIPS state and county codes) is the first whose tests are a `tests.yaml` that `arc test` runs, with no Python self-test, and the first built from two vintages of one issuer's files. `library/ourairports` (OurAirports' airports with ICAO codes) is the first from a project rather than an issuing institution, filed in `library` under the dataset's own name, and the first whose release is the date of a git commit on the source's repository. `census/naics_2022` (Census's 2022 NAICS), hosted before the contract existed, was brought onto it on 2026-11-18, the first list to change shape after publishing. `census/naics_2022_titles` (Census's 2022 NAICS index file) is the first title index with a Protocol of its own, apart from its code list's, and `census/naics_2017_to_2022` (Census's 2017 to 2022 NAICS concordance) the first edition crosswalk with one. Read this before building any of them.

## What a hosted code list is

A code list is a ladder of codes, each pointing at its parent: a chapter, the headings in it, the subheadings in those, down to the lines other data carries. Meridian hosts one so an analyst can query it with SQL instead of reading a PDF or clicking through a lookup site.

The rule behind every hosted dataset: it is prepared as the best data asset for an analyst's insight, not limited to the shape or gaps of the issuer's file. Schedule B shipped as Census's ten-digit lines alone, with no headings, would technically work and would fail that rule. The preparation is done in the Protocol, in SQL on DuckDB wherever SQL can do it.

Two limits hold the rule to its sources. A gap is filled only from a source cleared for redistribution: the WCO's HS nomenclature and UN Comtrade are not, so the HS six-digit layer comes from US Government publications only. And every value brought in from a second source says where it came from, on the row and in the descriptor: a Schedule B heading whose text came from USITC carries `text_source = 'usitc'` and never reads as Census's own words.

## The contract

Every hosted code list leads with these ten columns, in this order, and adds its own after them.

| Column | Type | Meaning |
|---|---|---|
| `code` | VARCHAR, primary key | The code in the form other data carries it: digits only for HTS and Schedule B (`0101210010`, chapters `01`), hyphenated for US SOC (`11-1011`). |
| `code_display` | VARCHAR | The code as the issuer prints it (`0101.21.00.10` for HTS, `0101.21.0000` for Schedule B; the same as `code` for SOC). |
| `level` | VARCHAR, closed set per list | The level's name. |
| `depth` | INTEGER | 0 for the top level, one more per level down. |
| `parent_code` | VARCHAR | The `code` of the row one level up; NULL only at depth 0. |
| `description` | VARCHAR | The row's own text. |
| `description_full` | VARCHAR | The row's text with its ancestors' in front, joined with ` › ` (space, U+203A, space), so a line printed as "Other" reads in context. |
| `release` | VARCHAR, not null | The issuer's release this row was built from. |
| `text_source` | VARCHAR, closed set per list | Whose text `description` is. |
| `corpus` | VARCHAR | `description_full` lowercased and accent-stripped, the field the in-browser search reads. |

The `code` rule is one question: in what form does the data an analyst will join this list to carry the code? The answer differs by list, and the rule does not. Trade data carries HTS and Schedule B codes both dotted and as digits, and digits join without a rewrite, so `code` is digits only. US occupation data carries SOC codes with BLS's hyphen (BLS's OEWS wages, O*NET's `11-1011.00`, the Department of Labor's filings), so `bls/soc_2018`'s `code` is `11-1011` and `code_display` is the same; Census's ACS carries digits with `X` placeholders that match no code in either form, so it does not decide the question. UK occupation data carries ONS's plain digits, so `ons/soc_2020`'s `code` is `1111`, stored as text. `code` is VARCHAR on every list, so a leading zero or a hyphen is never lost.

A descriptor marks itself a code list with a package-level key naming its levels from the top down, set in its `descriptor.overrides.json`:

```json
"x-meridian-code-list": {"levels": ["chapter", "heading", "subheading", "commodity"]}
```

`scripts/check_code_list.py` holds a built Parquet to the contract, one SQL query per rule. It refuses a file with no rows; a missing core column or one out of order; a repeated or NULL `code`; a `parent_code` that is not a `code` in the same file; a NULL `parent_code` below the top level; a child whose `depth` is not its parent's plus one; a row whose `depth` is not its `level`'s position in the declared levels; a `level` outside the declared set; a NULL `release`, or more than one distinct `release` in the file; a NULL `description`.

It runs in two places. Each code-list Protocol runs it as its `check_code_list` step (`op: uv@1`, the script pinned by sha256, with `--parquet` and `--levels`), so a build that breaks the contract fails the run before it is validated and stamped. The lake check (`.github/workflows/lake.yml`, through `scripts/lake_check.py`) runs it with no arguments, after a merge, weekly and on demand: it reads every descriptor the lake check emits into `datasets/*/datapackage.json` that carries `x-meridian-code-list` and checks the object each one serves. A code list that breaks the contract there is drift and fails the run. Which datasets are code lists is read from their descriptors, never from a list in the script, so a new list opts in by declaring the key. A sweep that finds no code list exits 2, and CI counts that as a failure. `scripts/test_check_code_list.py` runs the check on deliberately broken fixtures.

Editing the script changes its digest, so every Protocol pinning it needs its `sha256` updated in the same commit (`shasum -a 256 scripts/check_code_list.py`).

## The job-title index contract

A job-title index is a table of names pointing at codes in a code list, for an analyst coding free-text job titles (job postings, HR extracts, survey answers). It leads with these seven columns, in this order, and adds its own after them.

| Column | Type | Meaning |
|---|---|---|
| `entry_id` | VARCHAR, primary key | The issuer's id for the entry where it has one (ONS's `UNIQUE ID`); otherwise the code and title together (`<code>\|<title>` for BLS). |
| `title` | VARCHAR, not null | The title as the issuer prints it. |
| `code` | VARCHAR, not null | The code it points at, in the code list's own form. |
| `code_description` | VARCHAR | That code's `description` in the code list, so a lookup needs no second join. |
| `release` | VARCHAR, not null | The index's release. One distinct value per file. |
| `text_source` | VARCHAR | Whose text `title` is. |
| `corpus` | VARCHAR | The title with any qualifiers the issuer codes it by, lowercased, accent-stripped and with runs of whitespace collapsed, the field the in-browser search reads. |

A descriptor marks the table with a package-level key naming the code list it points at, set in its overrides:

```json
"x-meridian-title-index": {"codeList": "bls/soc_2018"}
```

`contracts/check_titles.sql` holds the exported index to the contract, as a `sql:` step inside the Run. It fails the run on no rows; a missing or misordered core column; a NULL or repeated `entry_id`; a NULL `title`, `code` or `release`; a `code` that is not a `code` in the code list built in the same Run; a `code` whose level in that list is not the level the issuer codes titles to (detailed occupations for BLS, unit groups for ONS, six-digit national industries for Census's NAICS index); or more than one `release`.

## The edition crosswalk contract

An edition crosswalk is a table of the issuer's own pairings between the codes of two editions of a list, for an analyst bridging data coded to the earlier one. It leads with these seven columns, in this order, and adds its own after them, such as ONS's shares.

| Column | Type | Meaning |
|---|---|---|
| `from_code` | VARCHAR, not null | A code of the earlier edition. |
| `from_description` | VARCHAR | Its title, as the issuer prints it in the crosswalk. |
| `to_code` | VARCHAR, not null | A code of the later edition, in the hosted code list's own form. |
| `to_description` | VARCHAR | Its title, as the issuer prints it in the crosswalk. |
| `from_edition` | VARCHAR, not null | The earlier edition (`2010`). |
| `to_edition` | VARCHAR, not null | The later edition (`2018`, `2020`). |
| `release` | VARCHAR, not null | The crosswalk's own release. One distinct value per file. |

`(from_code, to_code)` is the primary key. A descriptor marks the table with the two editions and the code list its `to_code` points at:

```json
"x-meridian-crosswalk": {"from": "2010", "to": "2018", "toCodeList": "bls/soc_2018"}
```

`contracts/check_crosswalk.sql` fails the run on no rows; a missing or misordered core column; a repeated `(from_code, to_code)` pair; a NULL `from_code`, `to_code`, `from_edition`, `to_edition` or `release`; a `to_code` that is not a `code` in the code list built in the same Run, or is one at a level other than the crosswalk's (detailed for BLS, unit for ONS, national industry for NAICS); a `from_code` that does not fully match the earlier edition's code pattern; or more than one `release`. The earlier edition is not hosted, so `from_code` is checked by its shape alone.

Every crosswalk row is a pairing the issuer published. A crosswalk Meridian inferred, such as one drawn from the job titles two editions' indexes share, would read as an official concordance and would not be one, so none is built.

### How a Protocol runs the two contracts

Each contract is one file of plain DuckDB SQL with no parameters, in `contracts/`, and a broken rule stops the Run with `error('<contract>: <rule>: <first offending value>')`, where `<contract>` is `titles` or `crosswalk` (`titles: code not in code list: 11-9999`). A Protocol runs it by relative path (`sql: ../../contracts/check_titles.sql`) after its own models have set up what it reads on the Run's connection:

- `check_inputs_code_list`, a step of its own, creates the view `contract_code_list` over the code list exported in the same Run (`build/stage/<code list>.parquet`). Both checks read it, so it is set up once, by one step.
- A title index or crosswalk built by a Protocol of its own, apart from its code list's, as `census/naics_2022_titles` and `census/naics_2017_to_2022` are, builds the code list in the same Run with the code list Protocol's own model, run by relative path, and points `contract_code_list` at that table (see NAICS index below).
- `check_inputs_titles` creates the view `contract_titles` over the exported index and the one-row table `contract_title_level(level)` naming the level the issuer codes titles to.
- `check_inputs_crosswalk` creates the view `contract_crosswalk` over the exported crosswalk and the one-row table `contract_crosswalk_shape(from_pattern, level)`: the earlier edition's code pattern (`^[0-9]{2}-[0-9]{4}$` for BLS, `^[0-9]{4}$` for ONS, `^[0-9]{6}$` for NAICS 2017) and the level `to_code` must be at.

Each check refuses a level or shape table that is not exactly one row with no NULL, and on success writes `contract_titles_result(rows_checked)` or `contract_crosswalk_result(rows_checked)`, which its step declares as what it produces. The contract's interface is these names, documented in `contracts/README.md`; `scripts/test_contracts.py` runs every rule against small in-memory tables in CI. A rule changed in either file changes it for every Protocol that runs it, which is the point: the same rules hold for every index and every crosswalk, as `check_code_list.py` is one script for every code list.

## How a code-list Protocol is laid out

A code-list Protocol is a directory under `datasets/`, named after the dataset, holding `arcform.yaml`, `models/`, a `README.md` with the generated step list, `descriptor.overrides.json`, `nominations.finetype.json` and `schema.finetype.json`. Its steps, in order:

1. **Fetch, with the release recorded.** `http_fetch@1` of the issuer's file, plus whatever names the release (below), with the Meridian User-Agent on every fetch.
2. **Shared SQL, only where a source quirk is shared.** For the two lists here, `outline` runs `datasets/hts/models/outline.sql` (see "When SQL is shared").
3. **`load`**, a `models/load.sql` of the list's own. It reads the issuer's file, builds the ladder with a parent one level up for every row, the text and `description_full`, and the release, and fails the run with DuckDB's `error()` on any condition that would publish a wrong release or a wrong text.
4. **`package`** (`models/package.sql`) adds `corpus` in its place after `text_source` and hands off the terminal table.
5. **Export**: `parquet_export@1`, zstd, `order_by: code`, so the bytes before stamping are reproducible. (Schedule B's published file is not reproducible after stamping: see Known gaps.)
6. **`describe`**: `datapackage_describe@1` emits the descriptor from the Parquet, with the nominations and overrides applied.
7. **`check_code_list`**: the contract check above.
8. **`validate`**: `finetype_validate@1` against `schema.finetype.json`.
9. **`emit_descriptors`**: every published table's descriptor from the lake, into `build/lake_descriptors.json` (see "Before the publish" in [`docs/publishing.md`](publishing.md#before-the-publish)).
10. **`stamp_descriptor`**: writes the finished descriptor into the Parquet's footer, and to `build/datapackage.json`, keeping the lake's `created` when the file is the one the lake already serves.
11. **`check_before_publish`**: label agreement against the lake, Frictionless, the descriptor and licence rules against the local Parquet, and the overrides guard. A refusal stops the Run.
12. **`publish`**: `ducklake_write@1` into the open lake.

**HTS** (`datasets/hts/`) follows this exactly, in fourteen steps: three USITC fetches (`fetch_release_before`, `fetch_hts`, `fetch_release_after`), `outline`, `load`, `package`, `export_hts`, `describe`, `check_code_list`, `validate`, `emit_descriptors`, `stamp_descriptor`, `check_before_publish` and `publish`. Its `load.sql` takes chapter and section titles from the committed `chapters.csv`, derives subchapter rows from the outline, and fills ten-digit lines' rates from the line above that prints them.

**Schedule B** (`datasets/schedule_b/`) adds what its sources need, in nineteen steps: `fetch_schedule_b` and `extract_schedule_b` for Census's zip; `date_schedule_b`, which reads the date the zip records for `econcord.txt`; `fetch_index` for the year's index page, which holds the chapter and section titles; the same three USITC fetches as HTS; `outline` by relative path (`../hts/models/outline.sql`); its own `load` and `package`; and, after `describe` and `emit_descriptors`, `derive_join_coverage`, which measures the NAICS join against the published `census/naics_2022` object and writes its coverage into the descriptor, before the same closing steps as HTS. It keeps one writer per file: the export, describe and join steps write to `build/stage/`, and `stamp_descriptor` alone writes the published `build/schedule_b.parquet` and `build/datapackage.json`, so no step rewrites an earlier step's file and leaves it stale.

**HCPCS** (`datasets/hcpcs/`) is the first flat list, in fourteen steps: `fetch_hcpcs` and `extract_hcpcs` for CMS's quarterly zip; `date_hcpcs`; `load`, which reads CMS's fixed-width records by the record layout CMS ships in the same zip; `package`; `export_hcpcs`; `check_licence`, a `sql:` step over the exported file (see "When a source carries text that is not cleared"); `describe`, `check_code_list`, `validate`, `emit_descriptors`, `stamp_descriptor`, `check_before_publish` and `publish`. It keeps Schedule B's one writer per file: the export and describe write to `build/stage/`, and `stamp_descriptor` alone writes the published Parquet and `build/datapackage.json`. Its list has one level, `code`, so every row is at depth 0 with a NULL parent and `description_full` is `description`; the contract admits this, since `--levels code` declares a ladder of one.

**NDC** (`datasets/ndc/`) is the first list whose source is JSON and the first refreshed on a fixed schedule rather than at each issuer release, in twelve steps: `fetch_ndc` and `extract_ndc` for openFDA's NDC zip; `load`, which reads the finished drugs' listings into three levels, `labeler`, `product` and `package`; `package`; `export_ndc`; `describe`, `check_code_list` (`--levels labeler,product,package`), `validate`, `emit_descriptors`, `stamp_descriptor`, `check_before_publish` and `publish`. It keeps the one writer per file. Its `code` is the eleven-digit NDC claims carry, padded 5-4-2 and digits only, at five digits for a labeler and nine for a product, so each level's code is the prefix of the codes below it and a parent is found by prefix, as in the HS lists; `code_display` is the FDA's hyphenated ten-digit form.

**SOC 2018** (`datasets/soc_2018/`) is the first Protocol that writes several tables (see "A Protocol that writes several tables"), in twenty-five steps: `fetch_definitions`, `fetch_titles` and `fetch_crosswalk` for BLS's three workbooks (the 2018 SOC definitions, the direct match title file and the 2010 to 2018 crosswalk); `load`, which reads every sheet as text from an explicit range with DuckDB's `excel` extension, fails the run if a header row is not where it was measured, and reads the releases; `code_list`, `titles` and `crosswalk`, one model per table; the three exports, then the three describes; `check_code_list` (`--levels major,minor,broad,detailed`); `check_inputs_code_list`, `check_inputs_titles`, `check_titles`, `check_inputs_crosswalk` and `check_crosswalk` for the two new contracts; and the three validates, then the three stamps. Its four levels are BLS's, `major`, `minor`, `broad` and `detailed`. `code` keeps BLS's hyphen. SOC codes are not plain prefixes: the broad occupation `11-3110` sits under the minor group `11-3000`, but `15-1210` under `15-1200`, and the detailed occupation `29-1221` under the broad occupation `29-1210`, not the `29-1220` its last digit would name. So a minor group's parent is its major group (`NN-0000`), a broad occupation's the highest minor group at or below its code that shares its first four characters, and a detailed occupation's the highest broad occupation at or below its code that shares its first five; `code_list` fails the run if a row below the top finds none, or if the parent is not also the last group of that level BLS prints above the row in its sheet, so a miscoded or misplaced group stops the run. `definition` is BLS's, on detailed occupations only. The title index has one row per direct match title, keyed `<code>|<title>`, with BLS's `illustrative` mark as a boolean: an `x` in either case is true, an empty cell false, and any other mark fails the run. The crosswalk is BLS's pairings at the detailed level as BLS prints them, unweighted, with each title's `(#)` or `(##)` kept.

**SOC 2020** (`datasets/soc_2020/`) has the same twenty-five steps, in the same order: `fetch_volume1`, `fetch_coding_index` and `fetch_relationship` fetch ONS's Volume 1 (the structure and descriptions of unit groups), Volume 2's coding index and the SOC 2010 to SOC 2020 relationship tables, each to a fixed path under `build/ons/`, so a refresh changes a URL and never a path a model reads. Its four levels are ONS's, `major`, `sub_major`, `minor` and `unit`, of one to four digits; each code is its parent's with one more digit, so `parent_code` is the code with its last digit dropped, and `code_list` fails the run if that is not a group at the level above. `description` is the title as Volume 1's descriptions sheet writes it, `group_description` ONS's description on every row, and unit groups carry `entry_routes`, and `tasks` and `related_job_titles` as lists of strings split from ONS's `~ `-bulleted cells. The title index is the coding index's coded entries, keyed by ONS's `UNIQUE ID`, with the additional and industry qualifiers ONS codes a title by as columns and in `corpus`, and ONS's coding fields after them (the default flag, the extended sub-unit group and its title, the codes in SOC 2010, SOC 2000, SOC 90 and ISCO-08, and the version that added or amended the entry). `load` fails the run on an index entry without a code that is not a cross-reference. The crosswalk is the unit-group sheet of the relationship tables, 2010 to 2020: one row per pairing with ONS's four shares (men and women, in the Labour Force Survey and the 2011 Census), and each 2010 group's "Total sample" row, which gives its four base counts, carried as `*_base` columns on each of its pairings rather than as a row. Every descriptor's `licenses` is `OGL-UK-3.0`, and its description carries ONS's attribution and says that Meridian prepared the table from ONS's files.

Both SOC code lists carry ancestor columns after the contract's ten: the code of each level above the row (`major_code`, `minor_code`, `broad_code` for BLS; `major_code`, `sub_major_code`, `minor_code` for ONS), NULL at the row's own level and below, so an occupation rolls up to its major group in one GROUP BY without walking `parent_code`.

**FIPS** (`datasets/fips/`) has twelve steps: `fetch_states` and `fetch_counties` for Census's ANSI state and county code lists, `fetch_gazetteer` and `extract_gazetteer` for its Gazetteer county file; `load`, `package`, `export_fips`, `describe`, `check_code_list` (`--levels state,county`), `validate`, `stamp_descriptor` and `publish`. It keeps the one writer per file. Its two levels are `state` (two digits) and `county` (five, the state's two and the county's three), the forms federal data carries, so a county's parent is its first two digits. Census's ANSI page serves only the 2020 vintage, which predates Connecticut's change of 2022, when nine planning regions (`09110` to `09190`) replaced its eight counties (`09001` to `09015`) as county-equivalents; data from ACS 2022 on uses the regions. So the ANSI lists are the base, since they are Census's code list and carry the Island Areas and Census's class and functional-status codes, and the 2026 Gazetteer, which covers the 50 states, DC and Puerto Rico in the current vintage, adds the counties ANSI lacks (`text_source = 'census_gazetteer'`) and decides a `current` column: true for a code it lists, false for a county in a state it covers that it no longer lists (Connecticut's eight, kept because older data uses them), NULL in a state it does not cover. `load` reads each file as whole lines split on `|` and finds each header by its text, so no check rests on scan order (the county file is longer than one DuckDB vector, see "Row order from a workbook"), and checks each file's header before its lines, so a changed header is reported as one. It fails the run on a county both files list under a different name or GNIS code, so a rename in a later vintage is decided by a person, and on a county whose state, or state abbreviation, the state file does not give. After the core columns come `state_code`, `county_code`, `state_abbr`, `gnis_code`, `class_code`, `functional_status` and `current`.

**OurAirports** (`datasets/ourairports/`) has fifteen steps: `fetch_release_before`, `fetch_tree`, `fetch_airports`, `fetch_countries`, `fetch_regions` and `fetch_release_after` for the release bracket, the git tree and OurAirports' three files; `verify`, a `sql:` step that writes one file and no table (see "How a release is recorded"); `load`, `package`, `export_ourairports`, `describe`, `check_code_list` (`--levels airport`), `validate`, `stamp_descriptor` and `publish`. It keeps the one writer per file. It is a flat list of one level, `airport`, as HCPCS is: one row per airport that carries an ICAO code (10,734 on 2026-11-16), `code` the ICAO code from OurAirports' `icao_code` column, never from `ident`, which OurAirports fills with a local or generated code where it has no ICAO code on record. `load` reads each CSV with every field as text and finds its header by its text, and fails the run on a changed header, fewer than 5% of the airports file's rows carrying an ICAO code (a guard against OurAirports dropping most of them, which every per-row check would pass; 12.4% on 2026-11-16), an `id` that is not an integer, an ICAO code that is not four capital letters or that repeats, a country or region OurAirports' own lookup files do not list or list twice, a region of another country, a type outside the five, a `scheduled_service` other than yes or no, coordinates out of range, an elevation that is not an integer, or an empty name. After the core columns come OurAirports' fields: `ourairports_id`, `ident`, `type`, the coordinates and elevation, `continent`, `iso_country` and `country_name`, `iso_region` and `region_name` (the names from OurAirports' `countries.csv` and `regions.csv`), `municipality`, `scheduled_service`, `gps_code`, `local_code`, `home_link` and `wikipedia_link`. `iata_code` and `keywords` are read only to check the header.

**NAICS** (`datasets/naics/`) has eleven steps: `fetch_naics` for Census's 2022 NAICS descriptions workbook; `load`, `package`, `export_naics`, `describe`, `check_code_list` (`--levels sector,subsector,industry_group,naics_industry,national_industry`), `validate`, `emit_descriptors`, `stamp_descriptor`, `check_before_publish` and `publish`. It keeps the one writer per file. Its five levels are Census's, read from the code's shape: two digits for a sector, then three, four, five and six digits down to the national industry. Census numbers three sectors as ranges, `31-33` Manufacturing, `44-45` Retail Trade and `48-49` Transportation and Warehousing, and prints no `31`, `32` or `33` row, so the prefix rule alone leaves their subsectors with no parent. A subsector's parent is the sector whose two digits it starts with or whose range covers them (311 under `31-33`), and below the subsector a code's parent is the code with its last digit dropped. `load` fails the run on a code of any other shape, a repeated code, a row with no title, a row below the top whose parent is not in the file, and a subsector no sector covers or two sectors cover. `description` is Census's title with the superscript `T` Census prints after trilaterally comparable titles removed; `title`, after the core, holds the same value under the name the table published before the contract; and `definition` is Census's paragraph about the industry, NULL on the 154 industry groups whose definition is that of the one NAICS industry under them. Ancestor columns follow, as on the SOC lists: `sector_code`, `subsector_code`, `industry_group_code` and `naics_industry_code`. Its `release` is the edition, `2022`, and `text_source` is `census`, as for the index and concordance below. Its tests are `datasets/naics/tests.yaml`, and the index's and concordance's `arc test` run its `load.sql` too.

**NAICS index** (`datasets/naics_2022_titles/`) is a title index with no code list of its own, in twelve steps: `fetch_index` and `fetch_naics` for Census's 2022 NAICS index file and its 2022 NAICS descriptions workbook; `load_naics`, which runs `census/naics_2022`'s own model by relative path (`sql: ../naics/models/load.sql`) to build the code list in the same Run; `load`, `titles`, `export_naics_2022_titles`, `describe`, `check_inputs` and `check_titles`, `validate`, `stamp_descriptor` and `publish`. It keeps the one writer per file. The contract's code list is the one built in the Run from Census's file, never the lake, and a change to how NAICS reads that file reaches both tables; the descriptions workbook is fetched twice, once by each Protocol. The table has the contract's seven columns and nothing after them: one row per index entry (20,373 on 2026-11-17, under 1,010 of the 1,012 national industries), keyed `<code>|<title>` as BLS's is, `code_description` the code's `title` in `census/naics_2022`, Census's name for the industry, which that list's `description` also holds. `title` is trimmed at its ends; inner runs of spaces are kept and collapsed in `corpus`. Census's 25 cross-references (`******` in the code cell, `Dealers -- see type`) name no code and are left out, as ONS's are. `load` reads the sheet from an explicit range and numbers no rows, so it does not depend on scan order past one vector (see "Row order from a workbook"), and fails the run on a moved header, an entry without a code or description, a code that is neither six digits nor `******`, and a `******` row whose text is not a cross-reference. Its `release` is the edition, `2022`: Census's file states no release, and the save time Excel wrote into the workbook's properties is not Census's statement of a revision.

**NAICS concordance** (`datasets/naics_2017_to_2022/`) is an edition crosswalk with no code list of its own, laid out as the NAICS index is, in twelve steps: `fetch_concordance` and `fetch_naics` for Census's `2017_to_2022_NAICS.xlsx` and its 2022 NAICS descriptions workbook; `load_naics`, `census/naics_2022`'s own model by relative path; `load`, `crosswalk`, `export_naics_2017_to_2022`, `describe`, `check_inputs` and `check_crosswalk`, `validate`, `stamp_descriptor` and `publish`. The table has the crosswalk contract's seven columns and nothing after them: one row per pairing Census publishes (1,150 on 2026-11-17, from 1,057 2017 industries to all 1,012 national industries of 2022), keyed `(from_code, to_code)`. The titles are Census's in the concordance, trimmed at their ends and otherwise as printed, its misspelling `excpet` in 531120's titles included; a split 2017 industry's title names the piece that went to each 2022 industry (`Anthracite Mining - anthracite surface mining`). Census marks splits and merges in bold and italics, which the table does not carry, since each is a count over it, as BLS's `(#)` marks are carried in its text and no column. Census's 2022 to 2017 file holds the same pairings, so it is not fetched and the one table serves both directions. `load` checks the title in A1 and the header in A3:D3, reads A4:D by explicit range and numbers no rows, and fails the run on a pairing without either code or either title, a code that is not six digits, and a value in columns E to Z, where Census's file holds whitespace (in E to I) and nothing else, so a column Census adds is not dropped unseen. Its `release` is `2022`, the edition it bridges to.

The 2017 edition is not hosted. The crosswalk carries Census's 2017 titles and checks the 2017 codes by shape, as SOC's crosswalks do for their earlier editions; a `census/naics_2017` code list is a dataset of its own, to add when an analyst needs the 2017 edition for more than the bridge. The concordance would then be held to it as its 2022 side is held to `census/naics_2022`.

Each Protocol's SQL has a self-test that runs the shipped models through Python `duckdb` over a reduced copy of the source files and checks the result with `check_code_list.py`: `scripts/test_hts_models.py`, `scripts/test_schedule_b_models.py`, `scripts/test_hcpcs_models.py`, `scripts/test_ndc_models.py`, `scripts/test_soc_2018_models.py` and `scripts/test_soc_2020_models.py`, each a CI job. The SOC self-tests also run the two contract checks over the index and crosswalk they build, and hold the committed descriptors to those tables (see "A Protocol that writes several tables"); their fixtures are cut-down copies of the issuers' workbooks, cut with `openpyxl` and committed under `scripts/testdata/`, each with a README saying what was kept. The SOC Protocols publish themselves, through a last `publish` step (see [`docs/publishing.md`](publishing.md)); the four earlier lists, once published from outside the Protocol by infra's pipeline, moved to the same step on 2026-11-15.

### Tests a Protocol carries itself

FIPS has no Python self-test. Its tests are `datasets/fips/tests.yaml`, which `arc test` (arcform main from `c57f7bf`, the workflow's `ARC_REV`, in no tagged release yet) runs from the Protocol's folder: each test runs the Protocol's real steps in a copy of it, with checked-in fixtures in place of the fetches and the publish step left out, and asserts that the run succeeds with its inline `checks:` returning no rows, or that it fails with a given message. A `break:` rewrites a fixture with SQL before the run, so a refusal is shown to fire without keeping a broken copy of the file, and arc reruns each break with the change left out to show the failure comes from it. The next list should be tested the same way, as OurAirports' `datasets/ourairports/tests.yaml` is; its `arc test` runs locally until it joins CI's `protocol-tests` matrix, a one-line change to the workflow. `datasets/naics_2022_titles/tests.yaml` is in that matrix beside FIPS's. What carries over:

- **Fixtures** are cut-down copies of the issuer's files under the Protocol's `testdata/`, with a README saying what was kept, and named for a format arc can rewrite (`.csv`, `.tsv`, `.json`, `.xlsx`). Census's files are pipe-delimited `.txt`; their fixtures are `.csv` files holding the same text, and arc places each at the `.txt` path its fetch writes, where `load` reads it. A zip is fixtured as a zip, so the extract step runs on it; a test that breaks the extracted file gives the extract step a fixture of its own as well.
- **The pass case's checks are the self-test's assertions**, as SQL over the terminal table, comparing with `IS DISTINCT FROM` so a NULL cannot pass a check by accident, and with a check that the rows the others name exist.
- **A refusal test matches `load`'s own `error()` text**, so each refusal has a message that names what it found. A refusal raised inside a `uv` or `command:` step can be matched only by arc's `step '<s>' failed (exit code n)`, so the shared `check_code_list.py` contract is tested by `scripts/test_check_code_list.py`, and a Protocol's tests show only that its table meets it.
- **CI's `protocol-tests` job** builds `arc` at the workflow's `ARC_REV` and runs `arc test --junit` in each Protocol it lists, with finetype's release binary and DuckDB extension, `uv` and DuckDB's command line; a Protocol with a `tests.yaml` joins its matrix by a one-line edit to the workflow's `protocol` list, as FIPS, OurAirports, NAICS, the NAICS index and the NAICS concordance have.

### Describing, registering and publishing a list

Beside the Protocol, a new list needs these files and entries. HTS's and Schedule B's are the models to copy.

- **`descriptor.overrides.json`**, the curated half of the descriptor that `describe` lays over finetype's inference. It carries the package's name, title and description; `licenses` (for a US Government work, `other-pd`, titled for the issuer, such as "Public domain (U.S. Census Bureau)", pointing at the issuer's terms page); `sources` (the issuer's page for the list and the file fetched, plus every second source a value comes from, as Schedule B lists USITC's export for its heading text); `contributors` (the issuer as author, any second source as contributor, Meridian as publisher and wrangler); a `description` for every field, saying where its values come from and what NULL means on rows that lack it; `primaryKey` on `code`; and `x-meridian-code-list`. Where an issuer asks for a credit, the description gives it: Schedule B's credits the U.S. Census Bureau and says Census's bulk file carries no endorsement notice. A licence that asks for a notice (an attribution line, a statement of changes, the licence's text) carries it on the `licenses` entry as [`docs/licence-notices.md`](licence-notices.md) describes. A field whose shape is fixed declares it here as `constraints`, so the published descriptor states the shape the column holds rather than finetype's broader one.
- **`nominations.finetype.json`**, the columns whose finetype label is declared rather than inferred. Nominate a column only where inference gets it wrong, or cannot get it right from the values alone, and give each nomination a reason that is true of the data. Both lists nominate `code` as `geography.transportation.hs_code`: inferred from the values it is `unknown`, since a two-digit chapter and a ten-digit line share no shape. Where the label's pattern does not admit every shape the column holds, `describe` widens it, the overrides declare the column's own shape, and the mismatch is a finetype issue (see Known gaps).
- **`schema.finetype.json`**, the drift contract `validate` holds each run's Parquet to. It enforces the same shapes and lengths the descriptor publishes, so a run whose data has moved away from the published declaration fails instead of publishing it.
- **`x-joins`**, for a join to another hosted dataset, in the form `datasets/edgar_gleif` uses (`cardinality`, `coverage`, `evidence`, `measuredAgainst`, `package`, and a `where` filter naming the rows the join applies to). `package` is the other table's descriptor at the website's address, `https://meridian.online/datasets/<namespace>/<name>/datapackage.json`, since no descriptor is committed here. Schedule B's `naics` joins `census/naics_2022`'s `code` on rows `where level = 'commodity'`. It is not a `schema.foreignKeys` entry, because a foreign key asserts that every value exists on the other side, and some of Census's NAICS codes are not codes of the 2022 edition. `coverage` is not written by hand: `datasets/edgar_gleif/scripts/crosswalk_join.py --write` measures it at build against the other object's hash, and the joins check in the lake workflow (`.github/workflows/lake.yml`, through `scripts/lake_check.py`) runs it against the published objects after a merge, weekly and on demand.
- **`datasets/registry.json`**: an entry with a new `uid`, the `schema` (namespace) and `name`, the title, the manifest URL and a `protocol` pointer to the `arcform.yaml`. A new issuer gets a held namespace (`kind: held`, the issuer's name, unclaimed), as `usitc` was added for these lists, and the namespace is added to `schemas` and `reserved`. `scripts/test_registry.py` checks the result.
- **`README.md`**: a row in the Datasets table and the address in the list above it.
- **`datasets/label-agreement.json`**: `scripts/check_label_agreement.py` reports every declaration that differs between packages sharing a label or a field name. Give a reason only for a difference that is true of both packages: a different population (Schedule B's `naics` holds Census's own codes and codes ending in X that `census/naics_2022` does not), a different storage choice for one concept (Schedule B's `agricultural` as a boolean, GLEIF's status as text), or one field name used for different concepts (`code`). A declaration looser than the data is a defect, and the fix is to tighten it, not to excuse it. Schedule B's `code` first carried finetype's widened `hs_code` pattern, which admits dotted forms and lengths no level has; it now declares digits only at 2, 4, 6 or 10 digits, bounded 2 to 10, and its line codes (`naics`, `sitc`, `end_use`, `hitech`, the units) declare their fixed shapes, with the drift contract enforcing the same.

**Publishing.** A list's descriptor is not committed: its stamp writes `build/datapackage.json`, the lake stores it, and `scripts/emit_descriptor.py` emits it (see "Where a descriptor lives" in [`docs/publishing.md`](publishing.md#where-a-descriptor-lives)). A new list ends in arc's `ducklake_write@1` step, after `emit_descriptors` and `check_before_publish`, and takes the one path [`docs/publishing.md`](publishing.md#from-a-branch-to-the-lake) describes: build and check on the branch with `arc run --force` and no credential, merge with its registry entries, README rows and label-agreement reasons, then publish from `main` with `arc run --publish`. `check_before_publish` runs the strict label-agreement check against the lake inside that branch run, so the reasons a new list needs are found before the merge and merge with it. Until the publish, the lake check reports the list's README row and reasons as awaiting publish rather than failing. Before descriptors left the repository, CI checked every committed descriptor and every README row count against the object the lake served, with no allowance for an object not yet published, so a list was either published from its branch before the branch merged, as the earlier lists were, or, as FIPS and OurAirports were, merged without its descriptor and published after, with its label-agreement reasons committed with the descriptor after the first publish. FIPS skipped the strict check before its merge and needed a second snapshot (see FIPS in [`docs/publishing.md`](publishing.md#fips)); OurAirports ran it on its branch, and its fields reopened eighteen existing reasons and needed two new ones. That path no longer applies. infra's publish pipeline, which published the four earlier lists through `scripts/publish_dataset.py publish`, is stopped since the open lake's cutover to that step. `fda/ndc`, `cms/hcpcs`, `usitc/hts` and `census/schedule_b` moved onto the step on 2026-11-15, so every hosted code list now publishes by `arc run --publish`.

## A Protocol that writes several tables

An issuer that publishes a code list, a job-title index and an edition crosswalk gets one Protocol that writes all three, as the two SOC Protocols do. Each source file is fetched once and loaded once; one model per table builds it from the staging tables; and each table is then exported, described, checked, validated and stamped on its own. arc skips a step whose inputs have not changed, so a refresh rebuilds only the tables whose sources moved.

**Per-table files.** The single-table names do not fit a directory that holds three tables, so every file a table's descriptor is made from carries the table's name as a prefix, beside `arcform.yaml`: `<table>.overrides.json`, `<table>.nominations.finetype.json` and `<table>.schema.finetype.json`, and the descriptor its stamp writes, `build/<table>.datapackage.json` (`datasets/soc_2018/build/soc_2018_titles.datapackage.json`), which is not committed. Each table has its own export, describe, validate and stamp step, named for it (`export_soc_2018_titles`, `describe_soc_2018_titles`, and so on).

**One writer per file.** The exports write `build/stage/<table>.parquet` and the describes `build/stage/<table>.described.json`; each table's `stamp_<table>` step alone writes its published `build/<table>.parquet` and its `build/<table>.datapackage.json`, with `--carry-created-from build/lake_descriptors.json` so a rerun that stamps the object the lake already serves keeps the lake's `created`. Both SOC Protocols are in `scripts/test_manifest_one_writer.py`'s `ONE_WRITER` list, which fails CI if two steps declare the same file.

**The release is an input arc records.** arc decides whether a step is fresh from the tables and files it reads, and it reads those from the model's SQL. Each SOC `load` writes one row holding every source's release (`bls_release`, `ons_release`), and each table's model `CROSS JOIN`s that row and reads its release column. A release read in a scalar subquery instead (`(SELECT release FROM bls_release)`) does not appear among the step's inputs, so a change of release alone, with every staged row the same, would leave the tables and their stamps fresh and the old release published. With the join, a release-only change reruns every builder and stamp after it; this was checked on both Protocols by changing only a release line.

**The contract inputs are set up once.** Both new contracts read the same `contract_code_list` view, so it is created by `check_inputs_code_list`, a step of its own after `check_code_list`, and not by each check's inputs model; `check_inputs_titles` and `check_inputs_crosswalk` set up only their own table and its one-row level or shape table. Each view reads the file the export wrote in the same Run, so the index and the crosswalk are held to the code list being built, never to an earlier publish and never to the lake.

**Models arc can parse.** arc 0.2.1 parses each `sql:` model to find what it reads and writes. A model it cannot parse runs, but arc warns "could not parse … treating as opaque step", records no inputs and no outputs for it, and, if its step declares `produces`, reruns it on every run because it cannot see the declared tables being written. Three DuckDB forms broke the parse during the SOC build: a `(DESCRIBE …)` subquery, an `E'…'` string, and `[*COLUMNS(*)]`. The contracts read a table's column order from `information_schema.columns` instead of `DESCRIBE`; ONS's `load.sql` builds a newline as `chr(10)` and a list of columns with `list_value(A, B, …)`, and writes lambdas as `lambda x: …`, which needs DuckDB 1.3, so both SOC manifests declare `engine_version: ">=1.3"`. A Protocol is finished when its run gives no parse warning and a second plain `arc run` skips every step. A `load` arc parses declares in `produces` the staging tables it writes (`bls_release, bls_definitions, bls_titles, bls_crosswalk`; `ons_release, ons_groups, ons_index, ons_relationship`), as every other parsed model declares its table, so the manifest says what each step writes and a step that writes something else is visible in review.

**Row order from a workbook.** Two models number rows in sheet order with `row_number() OVER ()` over `read_xlsx`: BLS's `load` gives each definitions row its `sheet_row`, which `code_list` holds each parent to, and ONS's `load` gives each relationship row the position that joins a pairing to the "Total sample" row above it. A window with no `ORDER BY` numbers rows in the order the scan delivers them, and DuckDB does not promise that order. It holds here because every populated row falls within the first 2,048 rows the scan reads, one DuckDB vector: BLS's definitions sheet has 1,447 populated rows, the last at row 1,455, and ONS's unit-group sheet 1,083, the last at the 1,083rd row read. On 2026-11-03 both gave the same numbers at 1, 4 and 8 threads, and BLS's matched each row's cell row as `openpyxl` reads it. The open range (`A9:D`) still reads on to the sheet's last row, so the scan is more than one vector; the populated rows are not. BLS's self-test holds a known row to its cell row (`15-1210` is row 68 of the fixture). A sheet whose populated rows run past 2,048, such as NAICS's, cannot rely on this: it needs an order the reader guarantees, such as reading the sheet in bounded ranges and numbering each from its start row, or a check that the numbers it gave match the workbook's.

**Per-table descriptors and the checks.** Before the publish, `check_before_publish` reads each built `build/<table>.datapackage.json` as a package of its own, so the descriptor rules against the local Parquet, Frictionless and the overrides guard all hold it. Label agreement does not: its coverage is each Protocol's `datapackage.json`, as it was when descriptors were committed, and bringing the six SOC tables in is a change of its own, with the reasons their labels need. After the publish, the lake check reads the per-table descriptors it emits for the README catalogue check, which counts the rows of the object each row links to, the licence-notice rule, and the engine check. Beside those, each Protocol's own steps hold its tables to their contracts, and its self-test's `OverridesTest` holds each `<table>.overrides.json` to the table the models build: its fields are that table's columns in order, and its primary key, contract declaration (`x-meridian-code-list`, `x-meridian-title-index` or `x-meridian-crosswalk`, and no other table's), licence and field descriptions are the ones it gives, with no field undescribed; the release the models build is the one the overrides' `release` description quotes; and every URL the manifest fetches is among the sources of each table built from it. The self-tests held the committed descriptors to the built tables while there were any; with none committed, `describe` derives each descriptor from the table it describes, and the overrides it is made from are what the tests hold.

**Published by the Protocol's own step.** `scripts/publish_dataset.py` and CI's served-object checks assume one `datapackage.json` per Protocol directory. Rather than teach that seam to publish several tables, SOC waited for arcform's publish step, which writes several tables from one Protocol as one snapshot, and was published by `arc run` alone on 2026-11-14. Its registry entries, the held namespaces `bls` and `ons` and the README's Datasets rows went in with that publish; the dataset pages are still to come.

## How a release is recorded

Every row carries `release`, and a NULL fails the run, so a reader who pins a snapshot knows which revision of the codes it holds. How the release is found depends on what the issuer publishes.

**USITC's revision bracket.** USITC's export always serves the current revision and takes no release parameter; `currentRelease` returns the revision's name (`2026HTSRev22`). The Protocol fetches `currentRelease` before the export and again after it, and `load` refuses the run if the two names differ. A schedule that changed mid-download is never published under one revision's name. HTS's `release` is that name; Schedule B records the revision its heading text came from in `hts_release`.

**Schedule B's year and file date.** Census's file carries no release name. Each year's schedule sits in its own folder (`/schedules/b/2026/`), and `release` is the year folder and the date the zip records for `econcord.txt`: `2026/2026-07-27`. `archive_extract@1` does not set a member's date on the file it writes, so `date_schedule_b` (`scripts/member_date.py`) reads the date from the zip's own directory. It is the zip's recorded date, taken as recorded, because that is the one date that does not depend on who reads it. A zip records a member's date as a local date and time with no zone; Census's file records 2026-07-27 12:38, and 16:38 UTC in its extended timestamp, which agree on the day. A tool that shows the extended timestamp in local time far enough east shows the wrong day: `unzip -l` on an Australian clock shows 2026-07-28.

**The year guard.** The year is the Protocol's `year` param, default `2026`, which `load` stamps into `release` and checks against USITC's revision. arc does not substitute a param into an operator's `with:`, so the year appears in four places, and a new January folder changes all four: the param's default, `fetch_schedule_b`'s URL, `fetch_index`'s URL, and the year's index source in `descriptor.overrides.json` (its path and title). `datasets/schedule_b/scripts/test_protocol_year.py` fails in CI when they disagree. `load` also refuses a run whose index page title ("Schedule B 2026 - Browse Chapters") names a different year from the param, so `arc run --param year=2027` with the URLs left on 2026 stops rather than labelling 2026 data as 2027's.

**The edition guard and the January rollover.** USITC serves only its current revision, so around a new HS edition (the next takes effect on 1 January 2027) the Schedule B year and the USITC revision can belong to different editions. Schedule B's `load` refuses the run when the year in `hts_release` is not the Schedule B year, or when, outside chapter 98, USITC names fewer than 99% of the headings, or fewer than 99% of the subheadings, Schedule B implies. Each level is counted on its own, and a prefix USITC only labels counts as not named. A failed run publishes nothing: rerun once both issuers are on the same edition.

**CMS's quarter and file date.** CMS publishes each quarter's HCPCS file at its own URL, and the text file inside is named for the quarter. Up to October 2026 the name also carried the date CMS built the file (`HCPC2026_OCT_ANWEB_09232026.txt`); from January 2027 it does not (`HCPC2027_JAN_ANWEB.txt`). `release` is the quarter, read in `load` from the extracted file's name, and the date the zip records for the file, read by `date_hcpcs` with Schedule B's `scripts/member_date.py`: `2027-01/2026-11-12`. October's zip dated its file the same day its name did, so the release means what it meant before. The run fails if the directory holds other than one such file, if the name does not parse, or if no ISO date was written. A new quarter changes four literals in `arcform.yaml` (the URL, the zip member, the date step's member and `load`'s `depends_on`) and the quarter's source in `descriptor.overrides.json`; `scripts/test_hcpcs_models.py` fails when they disagree. A quarter is published on or after its first day, when its codes take effect, though CMS posts it about six weeks before; nothing in the Protocol checks the date.

**openFDA's last-updated date.** openFDA serves the current NDC directory at one URL, and its file's `meta` records the date openFDA last updated it and how many records the file holds. `release` is that date (`2026-10-30`); `load` fails the run if it is not a date, if the record count is not the count `meta` states, or if the extracted directory holds more than one file. The URL does not change, so a refresh changes nothing in the Protocol. The FDA updates the directory daily and Meridian refreshes it fortnightly, so the dataset's page and descriptor state the as-of date and that cadence. Because the row count moves with each refresh, the README states it rounded (`340K`), as GLEIF's is.

**BLS's title-block date.** BLS's 2018 SOC is a fixed edition that BLS revises in place under the same URLs, and its files' names carry no release. Each workbook states one in its title block, cell A4: the definitions file reads "November 2017 (for reference year January 2018 - Updated April 15, 2020)". The code list's `release` is `2018/2020-04-15`, the reference year and the update date, parsed in `load`; the run fails if the line does not parse, or if the direct match title file's A4 ("November 2017 (Updated April 15, 2020)") gives a different update date, since the index takes the code list's release. The crosswalk's A4 reads "November 2017", and its `release` is `2017-11`. A refresh changes nothing in the Protocol.

**Census's vintages in the file names.** Census names each FIPS source file for its vintage: `national_state2020.txt`, `national_county2020.txt`, and the Gazetteer's `2026_Gaz_counties_national.txt`. `release` names both, `ANSI 2020, Gazetteer 2026`, one value for the file as the contract requires, read in `load` from the names, so it cannot disagree with the files; the run fails if a name does not parse, if the ANSI state and county files are of different vintages, or if a folder holds other than one file of each. A new vintage changes the fetch's URL and `out` (and for the Gazetteer the zip member), `load`'s `depends_on`, and the sources in the overrides.

**The NAICS edition.** Census's 2022 NAICS index file has no title block and no date in its name, and sits under the `2022NAICS` folder. The only date in the file is the save time Excel wrote into the workbook's properties (2022-02-04), and Census's server answers with a `Last-Modified` from a site redeploy (2026-07-13); neither is Census's statement of a revision. NAICS 2022 is a fixed edition, so `census/naics_2022_titles`' `release` is the edition, `2022`. Census's 2017 to 2022 concordance has a title naming the two editions and no date, and its workbook's save time (2021-11-16) is no more a statement of a revision, so `census/naics_2017_to_2022`'s `release` is `2022`, the edition it bridges to. Census's 2022 NAICS descriptions workbook, which `census/naics_2022` reads, has no title block or date in its name either; its only dates are its save time (2021-12-30) and the server's `Last-Modified` from the same redeploy (2026-07-13), so its `release` is `2022` too. A refresh changes nothing in any of the three Protocols; NAICS 2027 will come as new files and new tables.

**OurAirports' commit and blob check.** OurAirports' files carry no date, and OurAirports commits them to the `main` branch of its data repository on GitHub; GitHub records a commit only when the files change, and in practice `airports.csv` changes nightly. Two fetches of the branch's latest commit from GitHub's commits API bracket a fetch of the git tree of the repository's top folder from its git trees API, which gives each file's git blob sha, and the three CSV fetches from `raw.githubusercontent.com`. `verify` refuses the run unless both fetches name the same commit, each commit date parses, each CSV's git blob sha, computed in DuckDB over the bytes fetched, equals the tree's, and the tree, hashed in DuckDB as git hashes a tree, is the one the commit names (`commit.tree.sha`), since GitHub's API answers are cached for a minute and the commit and the tree could otherwise come from different moments; it then writes the commit and its UTC date to `build/ourairports/release.csv`, and `release` is that date (`2026-11-16`), the UTC date of the commit OurAirports last made before the run. A bracket on the commit alone would not be enough: `raw.githubusercontent.com` caches each file for up to five minutes, so a run just after OurAirports' nightly commit could be served the previous night's bytes under the new commit, and publish yesterday's data with today's date. The blob check holds the bytes to the commit. A run refused for that ("GitHub's cache may still hold the previous version") publishes nothing and is rerun later. The URLs do not change, so a refresh changes nothing in the Protocol.

**ONS's sidecar URL.** ONS issues each revision of a workbook under a new URL whose file name carries its date (`…excel20260827.xlsx`), or for the relationship tables its month and year (`…july2021.xlsx`). Each workbook is fetched to a fixed path, and `load` reads the release from the `url:` line of the `.arcmeta` sidecar `http_fetch@1` writes beside it, so the release is that of the file actually fetched: the code list's is `2020/2026-08-27` (the edition and Volume 1's date), the index's `v14/2026-08-27/v3` (its version, from cell B2 of the index's INFO sheet, its date and its revision) and the crosswalk's `2021-07`. The run fails if any of them does not parse. ONS reissued the coding index under the same date as `…excel20260827v3.xlsx`, correcting ten entries, so the index's release also carries the file name's revision suffix as a third part, `v14/2026-08-27/v3`; a file name with no suffix gives the two-part form. Without it, v3 would be published under v2's release. A refresh changes the URL in `arcform.yaml`, that workbook's source in the overrides, every description that quotes the release or a count (see Known gaps), and in `scripts/test_soc_2020_models.py` the URL constant for that workbook (`VOLUME1_URL`, `INDEX_URL` or `RELATIONSHIP_URL`, which a test holds to the manifest) and the releases its release tests expect (`test_release`, `test_staging_releases`).

## When a source carries text that is not cleared

An issuer's file can carry content the issuer does not own. CMS's HCPCS file is a US Government work except for two parts: the American Dental Association's CDT codes (the D series) and the American Medical Association's CPT. CMS's file carries no CPT code as a row, but it cites CPT codes in its cross-reference field and in some long descriptions. The pattern the HCPCS Protocol follows, for this and any later list with the same problem:

- **Drop what is not cleared at the point it is read**, in `load`: D-series rows, and cross-references that are CPT or D codes.
- **Redact, not drop, where the row itself is cleared.** A CMS descriptor that cites a CPT code by number is CMS's text about a Level II code, so the code stays and each CPT-shaped number is replaced by `[CPT code]`. `text_source` marks the row (`cms_cpt_redacted`), as it marks text from a second source.
- **Prove it on the exported file**, in a step of its own before `describe`, so a run that lets cleared-only content slip fails before anything is described or stamped. `check_licence` counts what it checked and fails on any D code, any code or cross-reference of the wrong shape, and any CPT-shaped number or D code left in the text.
- **Commit no uncleared content in fixtures.** The HCPCS self-test's fixture is cut from CMS's file with its CPT numbers replaced by made-up ones (`00000`, `0000T`) and a made-up dental record.

## When SQL is shared between lists

SQL is shared between lists for two reasons: a source quirk two lists share, and a contract every list of a kind must meet. The second is the two files in `contracts/`, `check_titles.sql` and `check_crosswalk.sql`, which every job-title index and edition crosswalk runs (see "How a Protocol runs the two contracts"); they are shared for the reason `check_code_list.py` is one script, that the same rules hold for every list. The first has one case: USITC's outline. The HTS export is an indented outline, not a table of parents, and both lists need it: HTS for its own rows, Schedule B for the heading and subheading text Census does not publish. So `datasets/hts/models/outline.sql`, owned by the HTS Protocol because HTS owns the source, reads USITC's JSON into two tables, `hts_outline` (one row per USITC row with its indent chain) and `hts_levels` (every 2, 4, 6, 8 and 10-digit prefix of a numbered code, with its text and `text_source`). The Schedule B Protocol runs the file by its relative path, which arc 0.2.1 and 0.2.2 were both checked to accept, and reads only those two tables, so their columns are a contract between the two Protocols. What only HTS needs, such as subchapter rows, is built in HTS's own `load.sql`, not in the shared file.

Every later list derives its own hierarchy in plain SQL in its own `load.sql`. What is reused across all of them is the contract, the check and this guide. A second shared file for a source quirk appears only when two later lists turn out to share one.

Two other ways were considered and declined. A library of shared DuckDB macros for every code list reads like dbt-utils: functions that are found only by reading them, and not how a Protocol states what it does. New arcform operations, `nest-by-indent` and `nest-by-prefix`, would be the framework's own place for a reusable step, but laid against the seven lists they would not be used regularly: an indent outline serves HTS alone, and the prefix shape differs list by list (NAICS's ranges, SOC's code pattern, FIPS's fixed widths). They do not earn a place in arc's public catalogue.

## The decisions, and why

Made with the operator during the design:

- **Rates verbatim as text, not parsed.** USITC's rates mix percentages, specific duties and compound forms; a parser is later work if it is wanted. Each rate column's description says the rate is as printed and that chapter 99 provisions (Section 301, 232 and others) can add duties to a line whether or not its footnotes name them.
- **Every level present as a row.** Both lists carry every chapter, heading and subheading their codes imply, HTS included: USITC prints a single-subdivision heading only through its longer code (heading `0409` appears only as `0409.00.00`, "Natural honey"), and the best-asset rule applies to that gap as much as to Schedule B's.
- **Digits-only `code`, the issuer's dotted form beside it.** Other data carries these codes both ways, and digits-only joins without a rewrite.
- **Parents by prefix, indent only for the path.** `parent_code` is the code one level up, which is always in the ladder, so `depth` is the level's position. USITC's indent is used only to build `description_full`.
- **Sections as columns, not rows.** `section` and `section_title` sit on every row; a Roman numeral is not a code other data carries.
- **Chapter titles from a committed copy.** USITC's export has no chapter rows, and its titles live only in its site's table of contents, which has no stable URL, so HTS carries them as `datasets/hts/chapters.csv`, copied with its date and source. The run fails if a chapter has no title there. HS chapter titles change at HS editions, so recopy the file at each one; the next takes effect on 1 January 2027. Schedule B's chapter titles come from Census's index page, which has a stable URL.
- **Schedule B reads USITC's export itself**, rather than Meridian's published `usitc/hts`, so it runs without the lake, and records the revision it used in `hts_release`.
- **Publish before merge.** CI checks every descriptor and README row count against the served object, so a new list is published from its branch before the branch merges. FIPS merged first and published after, on 2026-11-16, with no descriptor committed until it did (see "Describing, registering and publishing a list"). That no longer applies: no descriptor is committed, no pull request reads the lake, and a list is published from `main` after its merge.

Made during the build:

- **A made level's text comes from its outline node.** A level USITC prints only through longer codes takes the text of its node: the lowest outline row that is above every USITC row under the prefix and above none outside it, with the unnumbered headings between the parent's node and it in front (subheading `010511`: "Weighing not more than 185 g: Chickens"). `text_source` is `usitc_derived` in HTS and `usitc` in Schedule B.
- **The code label where no row belongs to the prefix alone.** Where the prefix's rows sit directly under a row shared with other prefixes, or under a numbered line of another prefix (`9824.01.01` above `982402`'s lines), the row is labelled by level and code ("Heading 9903", `text_source = 'meridian_label'`). Most such prefixes are in chapters 98 and 99, such as heading `9903`, but not all: subheading `8424.89`'s lines sit under "Other appliances:" together with `8424.82.00`. A first child's text is never used, because it describes one line and would read as the whole level's. The label applies only when there is no node; a single-line level that shares its node with its made parent keeps USITC's text (`040900`, "Natural honey"). When a made level's parent is a label, its text chain starts at the top of the chapter, so it can repeat a heading its siblings share (`982352`); that heading is a true ancestor.
- **`description_full` from outline rows.** It is the chapter title, then the row's subchapter where its chapter has them, then the defining USITC row's indent chain and its text. Each outline row appears once; two different rows with the same text ("Other:" under "Other:") both stay, because they are different levels of the outline. Subchapter rows (such as "I. CHEMICAL ELEMENTS") follow the chapter title for every row until the next subchapter or the chapter's end.
- **Rate inheritance.** A printed line that prints none of the three rates (general, special, column 2) takes all three from its nearest printed ancestor that prints a general rate, and `rate_from_code` names it, so an analyst joining ten-digit import codes gets the rate that applies. On 2026HTSRev22 only statistical lines do. A line that prints its own rate has `rate_from_code = code`.
- **Chapter 98 in Schedule B takes Census text.** USITC's chapter 98 rows are import provisions (US goods returned and similar); Schedule B's are export provisions (repairs, relief donations, military goods). Matching by prefix would give Schedule B's headings unrelated text, so they take the text of the Census line under them (`census_derived`).
- **Schedule B's multi-line levels are labelled.** A Census-derived level with several Census lines under it is labelled ("Heading 9802", `meridian_label`) rather than taking one line's text, by the same reasoning as the HTS label.
- **The edition guard per level at 99%.** Headings and subheadings are counted separately, so a shortfall at one level is not hidden by the other.
- **`agricultural` is true for `'0'`.** Census's layout prints `0` or `1` without saying which is which. Every line of chapters 1, 2 and 4 is `0`, and every line of chapter 3, fish, which USDA's definition of agricultural products leaves out, is `1`. `load` refuses any third value.
- **Indent is NULL on rows USITC does not print.** Chapters, derived levels and labels have no indent of their own, and the column's description says so.

Made for HCPCS, during its build (the operator was away; each is a ruling that can be revisited):

- **One level, no letter rows.** CMS publishes no titles for the letter a HCPCS code starts with (A transport and supplies, J drugs, and so on); those titles exist in commercial code books, which are not cleared. A level with no text of its own would add nothing a reader cannot get from `left(code, 1)`, so the list is flat.
- **Terminated codes kept.** CMS's file keeps every code it has terminated, with its termination date (1,322 of 8,770 in October 2026). An analyst joining historical claims needs them; `termination_date` is NULL for a code in use.
- **Modifiers left out.** CMS's file also carries 384 Level II modifiers (A1, AM, ...). They are not codes on this list, cannot sit on its ladder, and are a separate table if they are wanted.
- **CPT citations redacted, not the codes dropped.** Fifteen G, M, S and V codes in October 2026 (sixteen in January 2027) cite CPT codes in their descriptors. They include the prolonged-service codes G0316 to G0318, and dropping a cleared code to remove a citation would cost an analyst the code; replacing the numbers costs only the citation.
- **CMS's repeated fields as lists.** Pricing indicators (up to 4), type of service (5), laboratory certification codes (8) and cross-references (5) are lists, NULL where CMS prints none, as HTS's units and footnotes are. Manual and statute references, MOG and anesthesia fields are not carried.

Made for the NDC directory, during its build (the operator was away; each is a ruling that can be revisited):

- **openFDA's JSON, not the FDA's text files.** The FDA publishes the directory as two tab-separated files, encoded Windows-1252, which DuckDB 1.5.5 reads only through its `encodings` extension, installed from the network at run time. openFDA's download carries the same listings in UTF-8, records its own date and record count, and openFDA's licence page states the CC0 dedication the issue relies on. Its `openfda` block, which openFDA adds from RxNorm, UNII and other sources with their own terms, is not read.
- **Finished drugs only.** openFDA's download also holds unfinished drugs (21,645 listings on 2026-10-30): bulk ingredients and drugs for further processing, which are a separate FDA file, reuse product NDCs across firms, and are not the directory claims data joins to.
- **Three levels, labeler, product and package, with eleven-digit codes.** The labeler code and the product NDC are codes other data carries, and with them every package has a parent that is a real code. Padding to 5-4-2 is the HIPAA billing form, so `code` joins claims data without a rewrite, and the prefix rule gives the ladder; `load` refuses a run where two NDCs pad alike.
- **A product NDC with several listings is one row.** 903 product NDCs have more than one listing, one per labeling document. The product row takes the listing certified latest, then the latest marketing start, then the lowest `product_id`, and `listing_count` records how many there were; each package row takes its own listing's fields, so nothing a package was listed with is lost.
- **A labeler's row takes the name its listings give most often.** Names vary by listing (1,273 of 5,395 labeler codes on 2026-10-30), and the FDA's directory has no separate labeler table. Each product and package row keeps its own listing's spelling in `labeler_name`.
- **A product's text is composed from the FDA's fields.** The FDA has no single product title, so `description` is the brand name (openFDA's already ends with any suffix), the generic name in brackets where it differs, and the dosage form. `text_source` stays `fda`, since every word is the FDA's.
- **A package listed twice keeps its earlier start.** Four package NDCs appear twice in one listing with two marketing start dates.

Made for SOC, with the operator during its design:

- **US SOC's `code` keeps BLS's hyphen.** The contract's rule is the form other data carries, and for US occupation data that is BLS's `11-1011`: BLS's OEWS, O*NET and the Department of Labor's filings all carry it. HTS is digits only by the same rule applied to trade data, so the rule did not change; its answer did. UK SOC's `code` is ONS's plain digits, the form the Labour Force Survey carries.
- **Three tables per issuer: the code list, the job-title index and the edition crosswalk.** An analyst comes to SOC with coded data to label or roll up, with free-text job titles to code, or with data coded to an earlier edition to bridge, and each issuer publishes what each of those needs. The UK crosswalk is in because ONS publishes its own relationship tables.
- **Only the issuer's own pairings.** Every crosswalk row is a pairing BLS or ONS published. A crosswalk inferred from the titles two editions' indexes share would read as an official concordance and would not be one.
- **One Protocol per issuer, writing several tables.** A Protocol is sized to the work it carries: one fetch and one load of each file, and arc's skipping of fresh steps rebuilds only what moved. One Protocol per table would fit the publish pipeline and CI as they stand, but would multiply the fetches and manifests and shape the Protocol around the harness rather than the work. Reading the published code list from the lake, for the index and the crosswalk, was declined as well: it ties each build to the lake and to an earlier publish, as Schedule B's design avoided.
- **Publish by `arc run` alone.** SOC was built and its descriptors committed, then held back until arcform's publish step could write to openlake and publish several tables from one Protocol, rather than this work extending the publish seam. It published that way on 2026-11-14.

Made for SOC, during its design and build:

- **One shared SQL file per new contract**, in `contracts/`, so the same rules hold for every index and crosswalk (see "When SQL is shared between lists").
- **Per-table descriptors beside the Protocol, not `datasets/*/datapackage.json`**, so CI's served-object sweeps stayed green on an unpublished Protocol, with each self-test's `DescriptorTest` holding them meanwhile. That no longer applies: no descriptor is committed, and the stamp writes each under `build/`.
- **Both issuers in one change.** Neither publishes from it, so nothing about the UK attribution, which is settled at the publish, needed the UK work held apart.
- **Ancestor columns on both code lists**, so a roll-up to any level is one GROUP BY.
- **ONS's 2010 to 2020 unit-group sheet only.** It is the one an analyst uses to move old data forward; the reverse direction and the major, sub-major and minor sheets are later work if wanted.
- **The coding index's cross-references left out.** 231 entries say "see" another title or ONS's notes instead of giving a code: they point at a title, not a code, and are not index entries. `load` fails the run on any other entry without a code.
- **BLS's parents by code, held to the sheet.** The first rule written, a detailed occupation's code with its last digit set to 0, failed on `29-1221`, which sits under `29-1210`. The rule built (see "How a code-list Protocol is laid out") gives every one of the 1,424 rows below the major groups the parent BLS's own structure file, `soc_structure_2018.xlsx`, gives, and the sheet-order check catches a miscoded or misplaced group. A group BLS drops outright is not caught (see Known gaps); catching it would need the structure file as a second source, and was accepted as a limit, since the 2018 edition is fixed and revised rarely.
- **`description_full` keeps a title repeated across levels.** A broad occupation and its only detailed occupation often share a title ("Chief Executives › Chief Executives"); both stay, because they are different levels, as HTS keeps two outline rows with the same text.
- **BLS's `(#)` and `(##)` kept in the crosswalk's titles.** BLS's workbook does not define them, but in its file `(#)` ends the title of exactly the 2010 occupations that pair with more than one 2018 occupation, and `(##)` the same for 2018; the field descriptions say so, from the data.
- **Whitespace collapsed in `corpus` only.** Nine BLS titles carry internal double spaces; `corpus` collapses them for search, and `title` and `entry_id` keep BLS's text.
- **The index's key is ONS's id, not the title.** No coded entry repeats a title and both qualifiers, but ONS gives every entry a `UNIQUE ID`, and the key should not rest on the text staying unique.
- **Left out:** O*NET, which is CC BY with a modification notice and trademark rules, and a separate dataset if wanted; the ISCO-08 framework sheet of ONS's index, whose titles are the ILO's (each entry's ISCO-08 code, ONS's own mapping, is carried); and a finetype type for hyphenated SOC codes, which finetype is adding separately. Until it lands, SOC code columns are nominated `representation.identifier.numeric_code`, which `describe` widens, and their overrides declare the `^[0-9]{2}-[0-9]{4}$` shape.
- **Fixtures cut with `openpyxl`.** The self-tests' workbooks are cut from the issuers' downloads of 2026-11-03, keeping each sheet's name and its title block and header rows as the issuer prints them, so `load`'s header checks and release parsing run against the real layout; ONS's copies keep the issued file names, and the self-test writes each `.arcmeta` sidecar with the real URL, which a test holds to the manifest.

Made for FIPS, during its design and build, with the operator away (each can be undone before the first publish):

- **Two Census vintages, with the Gazetteer for Connecticut.** The 2020 ANSI lists alone would fail every join to current Connecticut data; the Gazetteer alone has no Island Areas and no class or status codes. Measured, the two agree on every county they share, so the second source adds rows and a flag, not text.
- **Connecticut's old counties kept and marked `current = false`**, since data from before 2022 uses them.
- **`current` is NULL, not true, where the Gazetteer does not cover the state.** The Island Areas' codes are in the ANSI list, but no current-vintage file says whether they still stand.
- **A name or GNIS code the two files disagree on fails the run**, rather than taking either file's text.
- **No area or internal point** from the Gazetteer: they are measurements, not codes, and are later work if wanted.
- **Tests by `arc test`, not Python.** `ARC_REV` moved to arcform main `f57ff3c`, which has `arc test`, in the workflow, the loader's `Cargo.toml` and its lock.
- **Merged before its first publish, with no descriptor committed.** The publish runs after the merge, so the branch could not carry a descriptor CI would hold to an object not yet served. Every list now merges before its publish, and none commits a descriptor.

Made for OurAirports, during its build (the operator was away; each is a ruling that can be revisited):

- **`iata_code` and `keywords` are not published.** IATA's code list is proprietary, so `iata_code` is never read into the table, and `keywords`, free text in which IATA codes appear as IATA codes (on 58 airports it holds the airport's own) and cannot be told apart from other words, is dropped with it.
- **`local_code` is kept**, although on 2026-11-16 it equals the IATA code on 1,712 of the 7,823 ICAO airports that have one, 1,525 of them in the US. It is the FAA's location identifier in the US, which IATA adopts for US airports, and another national authority's own identifier elsewhere: a public identifier OurAirports records as such, not a copy of IATA's list, and blanking it would remove the FAA identifier from most US airports. Its field description says what it is and that it is not an IATA code.
- **Country and region names from OurAirports' own files.** `country_name` and `region_name` come from OurAirports' `countries.csv` and `regions.csv`, joined on the codes the airports carry, so every code has a name and the run needs no second source.
- **Only airports with an ICAO code, in one flat level, `airport`.** 10,734 of OurAirports' 86,368 airports on 2026-11-16. The others have no code other data carries in ICAO form, and a full airport list keyed by OurAirports' `ident` is a separate dataset if it is wanted. A ladder of countries above airports was declined: country rows are not ICAO codes, and `iso_country` beside each airport joins to a country list without mixing two code systems in `code`.
- **The release is the commit's UTC date, held to the bytes by the blob check** (see "How a release is recorded"), so a run refused because GitHub's cache still serves the previous files is rerun later rather than published under the wrong date.
- **Data fetched from `raw.githubusercontent.com`, not the Pages site OurAirports links**, because the raw files are the branch's own and the blob check can hold them to it; the Pages site redeploys after each commit, on its own schedule.

Made for NAICS, when it moved onto the contract, with the operator away (each can be undone before the republish):

- **The range sectors keep Census's code, `31-33`.** `code` and `code_display` are both the range, as the table published it before the contract. The contract's rule is the form other data carries, and data coded at the sector level carries the range as Census prints it (County Business Patterns, BLS's QCEW); finetype's NAICS pattern admits the three ranges and nothing else of that shape. No `31`, `32` or `33` rows were invented, since Census prints none.
- **`description` became Census's title; `title` was kept; the paragraph moved to `definition`.** The contract's `description` is the row's own text, from which `description_full` is built, so it had to be the title. `title` stays, holding the same value, so a query that names it keeps working. Census's paragraph, which `description` held before, is `definition`: Census calls these texts definitions, and `bls/soc_2018` names the same thing `definition`. It is the one column whose meaning the contract forced to change, and a query that read `description` for the paragraph now gets the title. A new snapshot carries the change, so time travel still reaches the old shape, and the descriptor's description says what moved.
- **`corpus` follows the contract**, `description_full` lowercased and accent-stripped, as on every other list. It held the paragraph's words before, so the dataset page's search now matches names only; free-text business descriptions are what `census/naics_2022_titles`' index entries are for.
- **The publish replaces the table whole, once.** arc's publish refuses a reordered table, and the contract puts ten columns first, so the `publish` step sets `on_schema_change: replace` for the publish that carries the new shape, and it comes out in the change after it. A replace shows every row deleted and reinserted in the change feed. `scripts/check_lake_shape.py` reported only columns added before existing ones, no column dropped or retyped, and the lake's compatibility views `naics` and `source.naics`, `SELECT *` over the table, take the new columns (checked on a local DuckLake by dropping and recreating a table under such a view).
- **The lake fixtures hold the descriptor the publish will store.** The label-agreement reasons pin the new fields' declarations, so each Protocol's `testdata/lake_descriptors.json`, and `scripts/testdata/lake_descriptors.json`, carry `census.naics_2022`'s new descriptor rather than the one the lake held on 2026-11-17. Until the republish, a run's `check_before_publish` against the live lake, in any Protocol, reports those reasons as stale, so the republish follows the merge directly.

## Known gaps

- **finetype's `hs_code` pattern lacks the chapter and heading forms.** It admits 6, 8 and 10 digits but not the 2-digit chapter or 4-digit heading, so `describe` widens it and each dataset's overrides declare the shape `code` holds. This needs fixing in finetype.
- **Schedule B's published file is not reproducible byte for byte.** `describe` gives the `sitc` column a different `x-finetype-locale` from one run to the next. The stamped footer carries the descriptor, so the published Parquet's bytes and hash, and the descriptor's, change between runs over the same data. The data bytes before stamping do not move.
- **finetype's `ndc` pattern lacks the labeler and product forms.** It admits the ten-digit hyphenated layouts and eleven digits, which are the package forms, so `describe` widens it for `fda/ndc`'s `code` and `code_display`, and the overrides declare the shapes each holds.
- **The NDC refresh is not scheduled.** Each refresh is `arc run --force` and then `arc run --publish`, run by hand, as for every Protocol-built dataset, so the fortnightly cadence holds only as long as someone runs it.
- **`describe` records pattern-fit from before an override.** A field whose pattern an override replaces still reports how finetype's own pattern fitted.
- **arc 0.2.1 does not re-run a step when only a param changes.** After changing `--param year=...`, run with `--force`.
- **A BLS group dropped outright is not caught.** If BLS removed a broad occupation or minor group from its sheet and left its children, they would fall to the group before it, by code and by sheet position alike, which the sheet cannot tell from a real arrangement such as `29-1221` under `29-1210`. A miscoded or misplaced group, or a missing parent, does fail the run. Catching a drop needs BLS's `soc_structure_2018.xlsx` as a second source.
- **arc serves fetches from its shared cache.** arc 0.2.1 answered every SOC fetch from its shared fetch cache ("cached: … no transfer"), even with `--force`, so a run does not prove the issuer still serves those bytes. On 2026-11-03 a fresh `curl` of each of the six URLs with the Meridian User-Agent matched the fetched files by sha256.
- **The SOC descriptors are outside label agreement.** `check_before_publish` and the lake check compare labels across each Protocol's `datapackage.json` only, so a label on a `<table>.datapackage.json` that disagrees with another table's is not caught. The descriptor rules, Frictionless and the overrides guard hold them before each publish; the README catalogue check, the licence-notice rule and the engine check hold them in the lake check.
- **`finetype_validate@1` passes when its schema file is missing.** At arcform `f57ff3c`, a `validate` step whose `schema.finetype.json` did not exist reported success, so a deleted drift contract would let a run publish unvalidated. Each Protocol here commits its schema; the fix belongs in arcform.
- **FIPS's `current` comes from the Gazetteer's coverage.** A state is current if the Gazetteer lists a county in it, so a state with no counties in a future Gazetteer would read NULL, not false.
- **SOC descriptions quote releases and counts a refresh must update.** Several field and package descriptions quote today's release (`v14/2026-08-27/v3`, `2017-11`) or counts (231 cross-references, 32,439 coded entries, 369 groups, 714 pairings). A refresh that changes them must edit the overrides; each `OverridesTest` fails if the release the models build is not the one the overrides' `release` description quotes, and if a fetched URL is not among the sources of the tables it feeds, but it does not check the counts.
