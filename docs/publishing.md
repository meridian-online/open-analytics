# Publishing into the open lake

How an open dataset reaches readers: a Protocol's last step writes it into the open lake, and nothing outside the Run takes part. The two Standard Occupational Classification Protocols, `datasets/soc_2018` (`bls/soc_2018`, `bls/soc_2018_titles`, `bls/soc_2010_to_2018`) and `datasets/soc_2020` (`ons/soc_2020`, `ons/soc_2020_titles`, `ons/soc_2010_to_2020`), are the first to publish this way, and the open lake was cut over to it on 2026-11-14 for their first publish. Every open Protocol has since moved onto the step. This guide says how the step publishes, what a publisher needs, the one path a change takes from a branch to the lake, where a dataset's descriptor lives now that none is committed, how the cutover ran and why in that order, the rulings behind it, each dataset's move, and what is left. Read it before publishing, or before adding a Protocol.

## The open lake

The open lake is one DuckLake catalogue on R2, in the bucket `meridian-open`, served read-only at <https://openlake.meridian.online/>. A reader attaches it without a credential:

```sql
INSTALL ducklake; INSTALL httpfs;
ATTACH 'ducklake:https://openlake.meridian.online/catalog/open.ducklake' AS meridian (READ_ONLY);
SELECT * FROM meridian.bls.soc_2018 LIMIT 10;
```

It holds three things per table: the table itself, under the catalogue's data path `https://openlake.meridian.online/lake/`; the table's descriptor in the catalogue's `meta` schema (`meta.descriptors`, `meta.fields`), with the package description as the table's comment; and a readable copy, a single Parquet file at `https://openlake.meridian.online/<namespace>/<name>.parquet`, for a reader who wants one file and no catalogue. Each Run's record is kept under `runs/`, and `manifest.json` at the root lists every dataset with its readable copy and the Run that wrote it.

**Readers need DuckDB 2.0 or later to attach the catalogue.** DuckDB 2.0's DuckLake extension writes the catalogue in a storage format 1.x cannot open, and arc's publish step writes with DuckDB 2.0. A readable copy is plain Parquet, and `read_parquet` reads it on any DuckDB.

## How a Protocol publishes

The last step of the Protocol is `publish`, of `op: ducklake_write@1`. In `datasets/soc_2018/arcform.yaml` it names the lake (`public_base: https://openlake.meridian.online/`, `catalog: catalog/open.ducklake`, `data_path: lake/`, `runs: runs/`, `manifest: manifest.json`), a local fallback (`local_catalog: build/lake/open.ducklake`), the tables, and the credential:

- `tables`: one entry per table, naming the SQL name it is published as (`bls.soc_2018`), the stamped Parquet the stamp step wrote (`build/soc_2018.parquet`), its descriptor (`build/soc_2018.datapackage.json`, under `build/` and never committed) and its readable copy (`bls/soc_2018.parquet`).
- `on_descriptor_change: fail`, on every table: before writing, the step compares the table's new descriptor with the one `meta.descriptors` holds, ignoring `created`, the resource's `bytes` and `hash` and each field's `x-finetype-confidence`, and prints each difference. It refuses the publish, writing nothing, when a field present in both has an `x-finetype-label` that moved, appeared or disappeared and the new field is not marked `x-finetype-nominated: true`; nominating the label in `nominations.finetype.json`, a committed input, is the fix. A labelled field new to the table, and a table the lake does not hold yet, are only reported. This catches finetype's inference drifting on the same data, which moved NDC's, Schedule B's and FIPS's labels before.
- `credential`: `type: r2`, `bucket: meridian-open`, and the names of the three environment variables that carry it, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY` and `R2_ACCOUNT_ID`.

The step reads only what the stamp steps wrote, so it runs after them, and after `check_before_publish` (see "Before the publish" below). It writes every table the Protocol names as one snapshot, upserting each on the `primaryKey` its descriptor declares (`code` for a code list, `entry_id` for a title index, `from_code, to_code` for a crosswalk), and commits nothing it has not finished: a publish that fails leaves the catalogue as it was. A Run over unchanged data commits nothing and says so. arc sets the readable copies and `manifest.json` entries in the same step, and writes `manifest.json`, the readable copies and any extra files with `cache-control: public, max-age=60` (readable copies and extra files from arcform PR 173 on), so a reader may see the previous version for up to a minute.

The Protocol declares `dotenv: [.env]`, so arc reads the three variables from a `.env` beside `arcform.yaml` as well as from the environment. An `.env.example` beside each Protocol names them with no values, and the root `.gitignore` ignores `.env` and its variants.

### The local fallback

With any of the three variables unset, `arc run` still finishes green. The step says it published locally, names the variables that are missing, and writes the lake into `build/lake/open.ducklake` instead, which attaches and reads back offline. This is how a Protocol is built and checked without a credential, on a laptop or in review.

### Publishing live

**With all three variables set, any `arc run` publishes into the live lake.** `--publish` does not switch publishing on; it only makes a missing credential fail the run instead of falling back to the local lake. So a filled `.env` is not kept in the Protocol folder, where every later run would pick it up. Keep the credential in a file outside the repository and export it for the publishing command alone, in a subshell:

```sh
(set -a; . /path/outside/the/repo/openlake.env; set +a; arc run --publish)
```

Three things a publisher must do first:

- **Publish with an `arc` at `ARC_REV` in `.github/workflows/descriptors.yml` or later.** Every Protocol sets `on_descriptor_change`, which an older `arc` refuses as an unknown field: `cargo install --locked --git https://github.com/meridian-online/arcform --rev <ARC_REV> --bin arc`.
- **A full run needs finetype's DuckDB extension built for DuckDB 2.0.** The `describe` and `validate` steps load it from `FINETYPE_DUCKDB_EXT`, which must point at the extension built for the DuckDB the Protocol runs on; an extension built for 1.x does not load.
- **After moving a Protocol to a new arc or DuckDB, force a rebuild before publishing.** arc skips a step it judges fresh, and a change of engine alone does not make a step stale, so the Parquet built by the old engine would be published as it stands. Run `arc run --force` with the credential unset, which rebuilds every step and publishes only locally, then publish. This happened with SOC: its builds had been written by DuckDB 1.5.6, a forced rebuild rewrote them on 2.0.0, and the descriptors were restamped from the new Parquet before the live publish.

`scripts/check_engine_version.py` holds each published footer's `created_by` to the DuckDB its Protocol pinned in its stamp steps (`duckdb==2.0.0` for every Protocol today) in the Run that published it, as the lake's run record states, over every table the lake holds, per-table SOC descriptors included. It runs in the lake check (see "The lake check" below), not on a pull request, so moving a pin on a branch reddens nothing; a copy written by the wrong engine fails the lake check and names both versions.

### What `manifest.json` still says

`manifest.json` stays, in the shape the website reads today, until the website reads the catalogue. arc's manifest writer sets only `catalog.url`. The top-level `updated`, `catalog.sha256_16` and `catalog.published` were written by infra's publish pipeline and stopped moving at the cutover; nothing on the website reads them, and infra's uptime monitor now checks freshness from the catalogue's newest snapshot and the pointer from `catalog.url` alone. A reader who pins the catalogue by `catalog.sha256_16` sees a stale hash. The fields retire with the manifest.

## From a branch to the lake

One pull request carries a Protocol change from its branch to `main`, and the publish runs from `main` after the merge. No step of it waits on another branch, and publishing one dataset changes no other branch's CI result. Before a publish, label agreement judges only what involves the tables being built: their own differences, and the reasons and corrections that name them. A reason that names a table the lake does not hold yet awaits that table's publish and is not stale, so two lists merged before either publishes can each publish on its own. One order remains: when a merged reason pins new values for a table the lake already holds and also names the table being published, publish the changed table first, since until then the lake still holds its old values and the reason does not match them. When both tables named by one reason have changed, publish them in two steps: merge a reason pinning the first table's new values beside the second's old ones and publish the first, then replace it with one pinning both new values and publish the second.

1. **Build and check on the branch.** Run `arc run --force` with no credential set and `FINETYPE_DUCKDB_EXT` pointing at the extension built for DuckDB 2.0. It runs every step, `check_before_publish` included, against the lake as it stands, and publishes into `build/lake/open.ducklake`. A refusal stops the Run before the publish step. Fix it with a committed input, such as a nomination, an override, or a reason in `datasets/label-agreement.json`, and commit that input with the change. The descriptor itself is not committed.
2. **If the table is already in the lake**, run `scripts/check_lake_shape.py` against the live catalogue (see "NDC, the first existing dataset to move") and stop on anything but `shape ok`.
3. **Merge once the pull request's CI is green.** No pull-request job reads the live lake (`.github/workflows/descriptors.yml` says what each one checks), so the branch is judged on the change alone: the checkers' self-tests, `arc test` for each Protocol that has a `tests.yaml`, each list's model tests, the README step lists and the registry. The constraint ratchet's refusal is no longer a pull-request job: it runs in `check_before_publish`, where the descriptor is regenerated. The README's catalogue row, the registry entry, the DuckDB pins and any label-agreement reasons go in on this branch too.
4. **Publish from `main`.** Export the credential for one command and run `arc run --publish` (see "Publishing live"). The Run emits the lake's descriptors again, restamps, runs `check_before_publish` against the lake as it is at that moment, and publishes.
5. **The lake check reports the gap until the publish.** `.github/workflows/lake.yml` runs on a push to `main`, weekly and when started by hand; a publish does not start it. The merge's push starts one. Whatever `main` now declares ahead of the lake (a README row count, a label-agreement reason, an overrides sidecar, a table not yet published) is reported as awaiting publish, and the run stays green. After the publish, start it with `gh workflow run lake.yml`. What the publish closed is no longer reported. Anything still awaiting publish belongs to a table not yet published, and anything reported as drift, such as a README row count that the publish's fresh data no longer matches, is fixed in a pull request of its own. A source whose rows move on every refresh, such as EDGAR or the crosswalk, has its README count written to a stated precision (`10K`, `0.2M`) that an ordinary refresh does not move, so such a pull request is needed only when the count crosses a rounding boundary.

A new Protocol ends in the same four steps as `datasets/fips`: `emit_descriptors`, the stamp with `--carry-created-from build/lake_descriptors.json`, `check_before_publish`, and `publish`, with its descriptor written under `build/`. It also declares `dotenv: [.env]`, keeps an `.env.example` beside the manifest, and regenerates its README's step list with `scripts/check_protocol_readme.py --write`. After moving a Protocol to a new arc or DuckDB, force a rebuild before publishing (see "Publishing live").

### Before the publish

Two steps run in every publishing Protocol before its `publish` step, and both need the lake.

`emit_descriptors` runs `scripts/emit_descriptor.py --all --bundle build/lake_descriptors.json`: every published table's descriptor, as the lake holds it, in one file keyed by table name. It reads the public catalogue and `manifest.json` with no credential. The stamp step reads `created` from that bundle (see "What `created` means" below), and `check_before_publish` holds the build to it. edgar_gleif's join measurement reads its siblings' descriptors (`edgar`, `gleif`, `naics`) from it too, rather than from files in the repository. The step declares the catalogue and the manifest as remote reads, so arc runs it on every Run, and the stamp, `check_before_publish`, the publish (which commits nothing when nothing changed) and edgar_gleif's join measurement re-run after it. That repeated work, and a small download each Run, was accepted rather than taught to arc as a freshness rule. Whether arc can judge a remote read fresh is a question for arc.

`check_before_publish` runs `scripts/check_before_publish.py` over each built descriptor and the Parquet it describes. It runs four checks, and any refusal fails the Run, so nothing is published:

- **Label agreement against the lake.** `check_label_agreement.py --strict` over the built descriptor beside every other table's as the lake stores it, with `datasets/label-agreement.json` as the reasons. A field labelled one way here and another way in the lake is caught before it lands, which is the check FIPS's first publish needed and did not have. Its coverage is each Protocol's `datapackage.json`, as it was when descriptors were committed: the six per-table SOC descriptors are left out, stated in the script and tested as a deliberate exclusion. Bringing them in would put SOC's labels before reasons nobody has written, so it is a change of its own.
- **Frictionless.** `check_frictionless.py` loads each built descriptor with the reference implementation, `frictionless==5.19.0`, against `datasets/frictionless-rejections.json`.
- **The descriptor and licence rules against the local Parquet.** `check_descriptors.py --require-self-description` reads each built descriptor against the Parquet just built: fields, types, constraints (an override's constraint the data breaks included), the primary key, `bytes`, the copy stamped in the footer, foreign keys, the licence rule and the licence-notice rule. The README catalogue rule is the lake check's. A built descriptor keeps the resource `path` it is published at, the `https://openlake.meridian.online/...` URL, and the check reads the local file in its place. Frictionless refuses an absolute local path, and the copy stamped in the footer states the published path, so rewriting the path would break both.
- **The overrides guard against the sidecar at the last published commit.** The constraint ratchet's rules, run on each built descriptor. A constraint the overrides sidecar (`descriptor.overrides.json`, or `<table>.overrides.json`) held when the lake's table was published, and which the built descriptor no longer carries, is refused unless the sidecar at `HEAD` declares the new value. That base is the sidecar at the last first-parent commit before the stored descriptor's `created`, since the lake's run records name no commit. A table the lake does not hold yet has no base. A constraint `HEAD`'s sidecar declares that the built descriptor does not carry is refused too. This keeps the refusal the ratchet made when the regenerated descriptor was committed: a sidecar entry dropped in one pull request and the looser descriptor published in a later Run is still refused. A pure deletion of a sidecar entry must therefore declare the looser value. The output names the base it used.

**`check_before_publish` needs the full git history.** The overrides guard reads the sidecar as it stood at a past commit, so the Protocol must be in a checkout whose history reaches back to the table's `created`. In a shallow clone the check stops with exit 2 rather than guess, which is why CI's `protocol-tests` job checks out with `fetch-depth: 0`. The base is dated on the current branch, so a table published from a branch other than `main` may have been published under a sidecar this base misses. Publishing from `main` after the merge is the path where the two agree.

A code-list Protocol also runs `check_code_list` on its built file, as before (see [`docs/code-lists.md`](code-lists.md)).

### Under `arc test`

`arc test` runs on every pull request for each Protocol with a `tests.yaml` (FIPS, OurAirports, the NAICS concordance and the NAICS index), and reads no network, so `emit_descriptors` is fixtured with a bundle under the Protocol's `testdata/` (`lake_descriptors.json`), as the fetch steps are. Its pass cases fixture `check_before_publish` with a stand-in report, because finetype labels a test's few fixture rows differently from the real data, and a build of fixture rows could never agree with the lake. One case in each of them runs the real check, with `describe` fixtured to the lake's own descriptor for that table, so the check is exercised end to end. FIPS's refusal case uses a second bundle (`lake_descriptors_disagreeing.json`) in which the lake disagrees with the build, and asserts that `check_before_publish` fails the Run.

A crosswalk's join measurement, edgar_gleif's `crosswalk_join.py`, takes its siblings' descriptors from the bundle, and `--descriptor SLUG=PATH` still replaces one. A slug the bundle does not hold is accepted only when `--package` names it too, which is the Protocol's own table on its first publish. Any other is refused, so a mistyped slug cannot pass for a table the lake has not seen yet.

### The lake check

`.github/workflows/lake.yml` runs `scripts/lake_check.py` on every push to `main`, weekly, and when started by hand (`gh workflow run lake.yml`). A publish does not start it, so a publisher starts it by hand after one. It gates no pull request. It emits every stored descriptor into a tree laid out like `datasets/` (`emit_descriptor.py --all --tree DIR --bypass-edge`), then runs over it the descriptor check with the README catalogue, the engine pin, label agreement, Frictionless, the code-list contract, every declared join, the constraint ratchet against `HEAD`'s overrides, and a full download and re-hash of every served object. `--bypass-edge` appends a query string to each readable copy's URL, so the check reads the origin and does not go red while the edge still holds an older copy after a publish.

It sorts each finding into one of two kinds:

- **Drift**: the lake contradicts itself, whatever `main` did since. A served object whose bytes or hash differ from its stored descriptor, a stored descriptor that disagrees with its object or with the copy in its footer, a footer written by an engine other than the one pinned by the Run that published it, a code list that breaks the contract, a declared join that fails, or a check that crashed. The run fails.
- **Awaiting publish**: a finding that compares the lake with a repository input (a README row count, a licence notice, a label-agreement reason, a Frictionless rejection, an overrides sidecar) when that input changed in git after the table's `created`, or a table not yet published. It is listed in the step summary and the run stays green. The same finding with the input unchanged since the publish is drift.

`lake_check.py`'s docstring names each finding's input. It reads each input's time from `git log`, so its job also checks out the full history. A README row count is dated by the last commit to that row's own line, and a label-agreement finding by the last commit to the reason or correction entry it is about, so an unrelated edit to either file after a publish does not turn a real mismatch into awaiting publish.

## Where a descriptor lives

No publishing Protocol commits a `datapackage.json`. Each table's descriptor, the full datapackage.org JSON, is stored in the lake, and the standard stays the interface: what any of the routes below gives is a datapackage.org descriptor, not a new format. The shipped `examples/` publish nothing, so they keep their committed descriptors.

- **In the catalogue**, `meta.descriptors` holds one row per table, with the descriptor in `descriptor` (and `meta.fields` one row per field). With the catalogue attached as in "The open lake":

  ```sql
  SELECT descriptor FROM meridian.meta.descriptors WHERE table_name = 'census.fips';
  ```

- **In the readable copy's footer**, under the key `datapackage.json`, so the file describes itself without the catalogue or this repository: `python scripts/stamp_descriptor.py read https://openlake.meridian.online/census/fips.parquet`, or `parquet_kv_metadata` in DuckDB, as the root README shows.
- **From the emitter.** `python scripts/emit_descriptor.py census.fips` prints the table's full descriptor, from the public catalogue, with no credential (it needs `duckdb` and `pyyaml`). `--out FILE` writes it to a file, `--all --bundle FILE` writes every table's to one file, `--all --tree DIR` lays each out where its Protocol names it, and `--catalog` and `--manifest` point it at another lake, such as a Protocol's local `build/lake/open.ducklake`.
- **From the website.** meridian.online serves each dataset's descriptor at `https://meridian.online/datasets/<namespace>/<name>/datapackage.json`, built from the lake when the site deploys, so `curl -O https://meridian.online/datasets/census/fips/datapackage.json` is the one command that needs no checkout. The descriptor footnotes on the dataset pages link there, and a crosswalk's `x-joins` `package` links point there (see "The address a join links to" below).

The stored copy and the footer copy leave out three fields that change with each file: the package's `created`, and the resource's `bytes` and `hash`. A file cannot state its own size or digest, since writing the value changes it. `manifest.json` records all three for each published table (`published`, `bytes`, `sha256`), and the emitter joins them back, so its output and the website's are the full descriptor. When the manifest retires, the same three come from the catalogue.

### What `created` means

`created` is when the published file was created, judged on the whole file. The stamp step keeps the `created` the lake's copy states (`--carry-created-from build/lake_descriptors.json`) when the file it stamps is byte for byte the object the lake already serves, so a re-run over unchanged data keeps it. Any other file takes the `created` that `describe` wrote, a first publish included. A republish that changes only the descriptor still rewrites the file, since the descriptor is in its footer, so it gets a new `created` though no data page moved, as HTS's restamps always did. The stamp reads the bundle `emit_descriptors` wrote, so `emit_descriptors` runs before the stamp.

### The address a join links to

A crosswalk's `x-joins` entries name the other table's descriptor in `package`. Those links are set in `descriptor.overrides.json` to the website's address, `https://meridian.online/datasets/<namespace>/<name>/datapackage.json`, since the GitHub file they used to name is no longer committed. A link changes in the lake only when its dataset next publishes. Until then, the live descriptors keep their GitHub links, which no longer resolve, and the lake fixtures under `scripts/testdata/` and each Protocol's `testdata/` hold the lake as it was captured, GitHub links included.

## The cutover of 2026-11-14

Before the cutover, infra's publish pipeline wrote the open lake from outside each Run: it uploaded each dataset's files, rebuilt the catalogue, flipped `manifest.json` to point at the new catalogue, and collected old versions. The live catalogue's data path named a local folder, where arc's step writes to the https path the files are served from, and DuckLake cannot change the data path of a catalogue it has written. The cutover handed the lake to arc's publish step, in this order:

1. **infra stopped rebuilding the catalogue, flipping the manifest, collecting old versions, rolling back and uploading on its own.** Each of those rebuilt or overwrote what arc now owns, and the version collector would have deleted data files the new catalogue registers. infra's pipeline refuses to run with a message naming the cutover; its scripts stay until every Protocol has moved. The uptime monitor moved to DuckDB 2.0 in the same change, since it has to read the catalogue after the rebase.
2. **Readers were told they need DuckDB 2.0 or later.** The website's `ATTACH` snippets say so. The rebase is itself a DuckDB 2.0 write, so a 1.x reader of the catalogue would be cut off from that moment, not from the first SOC publish.
3. **The live catalogue was rebased onto the https data path.** `arc lake rebase` wrote a copy of the live catalogue whose data path is `https://openlake.meridian.online/lake/`, carrying the eight datasets already published and their eight compatibility views, and the copy was checked locally: every table and view read back with the row counts the manifest recorded. It was uploaded over `catalog/open.ducklake` with a conditional write, `If-Match` on the ETag the S3 API gave for the live catalogue before the rebase read it (the S3 API's, since a CDN may alter the public response's), so a catalogue that changed in between would not have been overwritten. The uploaded object's sha256 matched the local copy, and the eight read back through it over https.
4. **The two SOC Protocols published.** `soc_2018` committed snapshot 2 and `soc_2020` snapshot 3, each with its three readable copies and its entries in `manifest.json` (eighteen entries in all). All six read back through the catalogue over https with the row counts the Runs reported, alongside the eight and their views, with the descriptors in `meta.descriptors` and `meta.fields` and the ONS attribution line in the UK tables' descriptors and comments.

The same sequence, the rebase of the real catalogue and both SOC publishes into it, ran first under a test prefix, `lake-test/`, and was checked the same way, including a re-run that reported nothing changed and left the catalogue's ETag as it was, and infra's monitor run against it. Everything under the prefix was then deleted, and nothing had been written outside it.

## Hugh's rulings

- **This session carried the cutover**, with the SOC publish, rather than SOC publishing into an interim catalogue to be merged later: the open lake is one catalogue, and a reader should attach once.
- **The cutover was rehearsed under a test prefix before the live lake was touched**, because `arc lake rebase` had never run on the real catalogue, and a fault there would first have appeared in the catalogue every dataset is read through.
- **The agent ran the writes to `meridian-open`**, with the credential kept outside the repository and exported only for each publishing command: the rehearsal straight through, and each production write (the conditional catalogue upload, each SOC publish) only after Hugh's go-ahead for that write.
- **The four hosted code lists move one at a time**, in the order NDC, HCPCS, HTS, Schedule B, NDC first because it changes fastest, each list reviewed and published on its own. **They merge as they go.** Publishing from a branch reddens every branch that lacks that restamp, so NDC and HCPCS merge together, in HCPCS's pull request, and HTS and Schedule B each branch from `main` after the previous merge, so every pull request is green when it merges.
- **Each live write waits for Hugh's go-ahead for that write**, as SOC's did.
- **NAICS moves with its columns unchanged** (2026-11-16). Bringing it onto the code-list contract renames and adds published columns, which changes what readers query, so that waits for a change of its own.
- **NAICS's live publish comes after a merge**, not from an unmerged branch (2026-11-16).
- **A publishing Protocol does not commit its `datapackage.json`; the lake stores it, and it is emitted on demand** (2026-11-17). The descriptor lived in two places, git and the lake, and every pull request's CI held one to the other, so a descriptor or pin change could not go green until it was published, one publish reddened every other open branch, and CI stayed red until the edge copy expired. Hugh: "Perhaps it doesn't need to be committed, but rather easily emitted. So, we support the standard and can render it quickly through CLI and other means but we just store it in the lake." What is emitted is the datapackage.org descriptor as stored, so no new format is made. This retires the two-pull-request moves and the publishes from unmerged branches recorded below.
- **A pull request's CI checks only what the change makes**, and whether the lake serves what is declared is checked on `main`, weekly and on demand, from the origin rather than the edge (2026-11-17).
- **The lake check reports the gap and fails only on drift** (2026-11-17), so `main` is not red after every merge while the publish that follows it is still to run.
- **The website reads descriptors from the lake**, in its own change, so no committed copy is left anywhere to go stale (2026-11-17).
- **meridian.online serves each dataset's descriptor at `/datasets/<namespace>/<name>/datapackage.json`, built from the lake when the site deploys** (2026-11-17), and the site's descriptor footnotes link there. Hugh had expected the website to read the lake for this ("I thought we decided the web could read the Lake for this?") and chose to have the site serve the file, so a reader gets the descriptor from Meridian's own address with no catalogue and no checkout. The site's build reads the lake at deploy time, so a lake outage blocks a deploy; Hugh accepted that.
- **A descriptor diff at publish belongs to arc's `publish` step, as an option**, not a step of its own (2026-11-17). arc's write already compares the table's shape with the live table's, and comparing the new descriptor with the stored one is the same comparison one level deeper; Hugh asked for it as "an integrity check provided as an option within `publish`". What it is for is inference drift, a label that moved when no input did; the data and the committed inputs speak for themselves. It is arc's change to make (see "What is left").

## NDC, the first existing dataset to move

`datasets/ndc` (`fda/ndc`) moved onto the step on 2026-11-15, and that publish was its fortnightly refresh. It was the first Protocol to publish into a table already in the lake: `fda.ndc` had been carried into the rebased catalogue in snapshot 1, so the step upserted into it rather than creating it. Snapshot 4 inserted 1,647 rows, updated 338,546 and deleted 1,339, leaving 340,193. Nearly every row updated because each carries `release`, openFDA's last-updated date, which moved; the deletions are listings openFDA no longer carries. The readable copy moved from its content-addressed key to the fixed `fda/ndc.parquet`, and its `manifest.json` entry with it. A re-run reported nothing changed.

Three things came up that the next move will meet:

- **A table already in the lake must keep its shape.** The step refuses a table whose columns were dropped, retyped or reordered (`on_schema_change: fail`, the default), and the rebuilt Parquet is only compared with the live table at publish time. `scripts/check_lake_shape.py` applies the same rule beforehand, and also stops on a row count more than 10% from the live table's: `python scripts/check_lake_shape.py --catalog https://openlake.meridian.online/catalog/open.ducklake --table fda.ndc --parquet datasets/ndc/build/ndc.parquet` prints `shape ok: fda.ndc 32 columns, rows 339885 -> 340193`. The tables the rebase carried have no rows in `meta.fields`, so arc has no stored key to compare and the descriptor's `primaryKey` becomes the key.
- **finetype's inference moved under DuckDB 2.0.** `describe` types each column from a sample, and on DuckDB 2.0 the sample read NDC's `depth` (0, 1, 2) as a word and `marketing_category` (ANDA, NDA, BLA) as month names, though the committed descriptor had them as an integer and text. It did so on finetype 0.6.64, 0.6.66 and 0.6.67 alike, so the version was not the cause. Both columns are now nominated in `nominations.finetype.json`, which keeps the labels they had. The descriptor records the version of the `finetype` binary on PATH as `x-finetype-version`, so `FINETYPE_DUCKDB_EXT` should point at an extension of the same version: DuckDB 2.0's community repository serves 0.6.66, and 0.6.67's extension is built from finetype's `v0.6.67` tag with `make build-extension`, which needs its `extension-ci-tools` submodule.
- **The CDN served the old readable copy after the publish.** arc before arcform PR 173 uploaded a readable copy with no `cache-control`, the zone caches everything for as long as the origin allows, and an edge copy of `fda/ndc.parquet` cached before the publish went on serving the old bytes, for up to Cloudflare's default edge TTL. The catalogue was not affected, since its data files are new keys. arc sets `cache-control: public, max-age=60` on readable copies from PR 173 on, so the lag now happens once per readable copy: on its first publish by such an arc, while the edge still holds the copy uploaded without the header, check its hash from the origin (a request with a query string bypasses the edge copy) and expect the plain URL to lag until that edge copy expires. After that, the plain URL revalidates within a minute.

## What is left

- **Every open Protocol has moved.** edgar_gleif was the last, on 2026-11-17 (see its section above). Each publishes by `arc run` alone, on DuckDB 2.0, and the engine check holds its footers to that pin.
- **infra's publish scripts and workflow can be deleted**, now that all of them have moved. Until they are, they refuse to run.

- **The SOC per-table descriptors join label agreement**, with the reasons their labels need (see "Before the publish").
- **Each crosswalk's `x-joins` links take the website's address at its dataset's next publish** (see "The address a join links to").
