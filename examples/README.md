# Demo Protocols — third-party data, referenced by URL, published nowhere

**Nothing in this directory is a Meridian dataset, and nothing here is a candidate to become one.**

Each subdirectory is an [arcform](https://github.com/meridian-online/arcform) Protocol that fetches a third-party file from its canonical URL, transforms it in DuckDB, exports a Parquet to the machine that ran it, and emits a Frictionless [Data Package](https://datapackage.org/) descriptor for what it built. They exist so that the analysis surface has real data to be demonstrated against, with a reproducible recipe behind it instead of a binary somebody made by hand.

**The distinction from `../datasets/` is the whole point of keeping them apart.** A Protocol under `datasets/` terminates in an object Meridian serves at `openlake.meridian.online`, and everything about the licensing of that act applies to it. A Protocol under `examples/` terminates on your disk. Meridian hosts none of this data, redistributes none of it, and adds no second URL for anything that already has one. Running one of these is the same act as running a shell script that curls a file — the licence question attaches to whoever runs it and what they do with the bytes, not to the recipe.

**The last five are the Protocols behind Brightfield's getting-started gallery.** Its front door opens each of them on a dashboard, and its `examples/starts/` takes its copy of each recipe from here, so a recipe is written once and the gallery and this directory cannot drift apart. The models keep the gallery's table and column names. Two of them Brightfield runs from a file it ships rather than from the issuer, Palmer Penguins and the USGS earthquakes, because its first screen opens without a network; the recipes here fetch from the issuer, and the USGS one makes the same cut Brightfield's file was made with (the USGS's own network, `net = us`, and events of type `earthquake`), compared row for row against that file when the recipe was written. `online-retail-ii` reads the Customer ID only to derive each customer's first month and order numbers, and no table it makes holds the ID.

**`medmcqa` and `supergpqa` compute the coordinates their map is drawn from; the other nine embed nothing.** `medmcqa` and `supergpqa` embed the column named in the *Map* row and reduce the vectors to `projection_x` and `projection_y` with UMAP, so a dashboard has a scatter of what the questions are about and a recipe behind it. Apple's Embedding Atlas gallery joins the same two columns in for these two datasets from a Parquet it built out of band; here they are steps in the pipeline. **Read those coordinates as regions and not as distances**, and note there is no `neighbors` column and none can be recovered from two coordinates — each of those two Protocols has its own `README.md` saying so at length, which the other nine do not.

**Those two also need one thing the other nine do not: an embedding extension on disk.** `text_embed@1` names a loadable DuckDB artifact the Protocol puts there and never downloads, and there is no published URL for it today, so it is the one input in this directory that does not arrive from a URL. Each of the two READMEs says how to build and place it; absent, the run stops in milliseconds naming the file it looked for.

**Each licence was read at its source, and for `movies` that turned out to mean no licence at all.** vega-datasets declares a per-resource licence for **58 of its 73 resources**, and `movies` is one of the 15 it does not — so the silence is a choice rather than an omission, and nothing is asserted here either. The BSD-3-Clause on that repository covers its code and infrastructure, and its own `datapackage.json` says so. An earlier version of this file labelled `movies` BSD-3-Clause and cited a `LICENSE` URL that returns 404; that was the repository's code licence applied to data it only redistributes, which is exactly the mistake this paragraph now exists to prevent.

**`scienceqa`'s own mirror disagrees with itself, and that is the other way this goes wrong.** The Hugging Face mirror's YAML frontmatter tags the dataset `cc-by-sa-4.0` — no NonCommercial — and a third-party gallery that read only that tag has the dataset catalogued as plain CC BY-SA. That mirror's own card *body*, three headings down under "Licensing Information," says CC BY-NC-SA 4.0, and the licensor's project site (`scienceqa.github.io`) and source repository (`github.com/lupantech/ScienceQA`) both agree with the body, not the tag. So `scienceqa/arcform.yaml` and its descriptor both carry NonCommercial, and both say plainly what it restricts: referencing this URL and building the Parquet is not redistribution and is not restricted; Meridian using the *output* commercially — on the site, in launch material, on a pricing page — is.

**`medmcqa` is the third instance of the same class, with a third surface in it, and it is why no licence is asserted for that one at all.** Its Hugging Face repository tags the dataset `apache-2.0` in YAML frontmatter; the same card's own *Licensing Information* section, read at revision `91c6572c`, says `[Needs More Information]` — the licensor declining to state terms; and the authors' own repository, `github.com/medmcqa/medmcqa`, carries an MIT `LICENSE.md` over a tree of `train.py`, `model.py`, `dataset.py`, notebooks and a `requirements.txt` with no data in it at all. Both mistakes this file already records apply at once: a tag is not the licensor, and a code repository's licence is not a grant over data it links to. So all three readings go into that Protocol's descriptor and it relies on none of them — referencing the URL needs no grant, and the output should be treated as unlicensed third-party content until someone has terms in writing.

**`supergpqa`'s licence asks for something none of the others do, and it is checked rather than written.** ODC-BY asserts no copyright over the underlying content; what it requires is credit to the original creators of the third-party data included, and the source card names **fifteen** datasets. All fifteen are in that Protocol's descriptor by name and by link, and `supergpqa/models/corpus.sql` stops the run when one goes missing from that file, naming which. Attribution is the obligation in this directory that a reader cannot verify by looking at the data, and the one a gate stops the run on. The NonCommercial restriction on `scienceqa` has a weaker gate: `scripts/check_descriptors.py` fails a descriptor that carries the clause without a sentence stating it, and cannot tell whether anyone obeys the sentence.

**`census-income` and `california-housing` are read from the bodies that publish them, not from the re-uploads they were first fetched from.** Both used to fetch a Hugging Face copy and carry that copy's tag: CC0 for one, MIT for the other. Neither tag was the issuer's. UCI, which publishes the Adult data, licenses it CC BY 4.0, so that descriptor credits Becker and Kohavi (1996) by DOI, links the licence and says what the recipe changed. StatLib, where Pace and Barry published the housing data in 1997, declares no licence for `houses.zip`, so nothing is asserted for it, as with `movies`. Fetching from StatLib also gives the full 20,640 districts where the re-upload carried a 16,640-row train split. Both changes were checked against the old files: the Adult rows are the same 32,561 and, run with the same arc and DuckDB, the old recipe and the new one build a byte-identical Parquet, and each of the 16,640 re-uploaded districts equals one of StatLib's 20,640 under scikit-learn's derivation of the averages. Neither issuer has revisions, so for these two the `sha256:` is the only record of which bytes the recipe was written against.

Every `sha256:` in these manifests was computed from the fetched bytes here, and the three Hugging Face URLs and the palmerpenguins one address a 40-character commit revision rather than a default branch, so the revision is pinned as well as the content.

**Two recipes carry no `sha256:` at all, because their issuers change the bytes at a fixed URL.** A Protocol pins what it fetches only where the issuer serves the same bytes at that URL from one day to the next. Epoch AI adds models to `notable_ai_models.csv` as they are released and publishes no dated snapshot of it; the file went from 1,079 rows to 1,082 between 25 and 26 October 2026. The USGS revises events after the fact, and every row of its query response carries an `updated` time; the latest revision to a 2025 event was a day old on 26 October 2026. A pin on either would refuse every cold run after the issuer's next change, and a snapshot kept here would be the redistribution this directory exists to refuse. So `epoch-ai-models` and `usgs-earthquakes-2025` read their source as it stands on the day they run. Without a pin arc revalidates a cached copy against the origin on each run, so a warm cache does not freeze them. Each manifest records the size, row count and sha256 its source had on 26 October 2026, as a record and not a check, and each first model checks what its SQL assumes instead: that every model has a name and a date and the file holds at least 1,000 rows, or that every event is in 2025 at magnitude 4.5 or above and between 8,000 and 9,000 are kept. Each of those checks was made to fail on an altered copy of the source before it was committed. Their exports are byte-reproducible for a given day's source, not across days.

`census-income` describes individuals recorded by the 1994 US Census. It is used here as a *shape of data*, and its columns use that instrument's categories rather than ones anybody would choose today.

## Running one

```sh
cd examples/movies && arc run
```

You need `arc` on `PATH` and a DuckDB the manifest's `engine_version` accepts. Each run writes into that Protocol's `build/`, which is git-ignored.

## Two things worth knowing before you rely on a run

**The exports are byte-reproducible, and `ORDER BY ALL` is why.** Two cold runs of all six Protocols produced identical SHA-256 digests — `5ab2c92b…`, `5d045223…`, `d840cba2…`, `d7677afc…`, and `f820a057…` and `2637b545…` for the two that compute a projection. Those two were rebuilt with arc v0.2.2, whose `text_embed` loads the subtoken extension on DuckDB 2.0, so their digests are not comparable with the others either. The `census-income` and `california-housing` digests come from a later rebuild, when their sources changed, run with arc at the revision CI loads manifests with and DuckDB 1.5.5; the engine moves the bytes of a Parquet with the same rows, so those two are not comparable with the earlier four. **A UMAP fit reproducing is a stronger claim than a sort reproducing**, and three things buy it rather than the ordering alone: the seed is frozen in `umap_project`'s script rather than exposed in a manifest, the thread count is pinned to one before numpy and numba are imported, and each Parquet is read single-threaded with insertion order preserved. On those two the ordering IS a total order — `medmcqa.id` and `supergpqa.uuid` are distinct on every row, and each Protocol's `models/load.sql` stops the run if that stops being true. On the older four it is not, and: 24 of `census-income`'s 32,561 rows, and 64 of `scienceqa`'s 4,241, are exact duplicates of another row, so ties exist. A tie between two rows that are equal in every column cannot change the output bytes, because the rows themselves are identical — which is the weaker condition that actually holds, and it holds without inventing a surrogate key. Broken and reproduced on `scienceqa`: swapping `order_by: "ALL"` for `order_by: "random()"` turned two consecutive runs' digests different (`72962916…` vs. `b4c7d1e3…`) where the real manifest gives the same digest every time. The five gallery recipes were rebuilt from an empty `build/` with the same arc and DuckDB 1.5.5 and reproduced their digests — `6cc7737d…` for `palmer-penguins`, `3f4771aa…` for `usgs-earthquakes-2025`, `7b95c698…` for `nyc-yellow-taxi`, `678dd5bc…` for `online-retail-ii` and `f0016863…` for `epoch-ai-models` — the last of them and the USGS one for their sources as they stood on 26 October 2026.

**A `sha256:` pin is provenance here, not an integrity gate.** On a genuine transfer it fails closed — corrupt a pin against an empty cache and the run stops, naming both hashes. But arcform's shared fetch cache is keyed by **URL**, and on a cache hit the pin is not consulted: with the cache warm, a manifest declaring `sha256: 0000…0` builds to exit 0 and reuses the cached bytes. Reproduced on `california-housing`. So the pin protects the first fetch on a cold machine and nothing after it, and changing a pin to name different bytes will not fetch them on a machine that already has the old ones.

**Rebuild by removing `build/`, not by deleting the exported Parquet.** Both work on a current `arc`: deleting the Parquet alone re-runs the export and describe steps and puts it back. On an `arc` built before 2026-08-19 it did not — the run reported every step fresh and left the file absent — so if a rebuild appears to do nothing, check `arc` is current before concluding anything about the Protocol.

## What finetype makes of them

The `describe` step types every column semantically, and the four tabular Protocols are a fair sample of what that buys and what it still gets wrong. `california-housing`'s coordinates come back as `geography.coordinate.latitude` and `.longitude` rather than as two doubles, and `movies.release_date` as `datetime.date.iso` — which is the difference between a dashboard that can choose a map and a date axis, and one that draws nine histograms. `movies.director` types as `identity.person.full_name`.

**The two projection Protocols say something the other four cannot, and it is about the map.** `california-housing`'s latitude and longitude come back as `geography.coordinate.latitude` and `.longitude`, which is what lets a dashboard decide on its own to draw a map. `medmcqa`'s and `supergpqa`'s `projection_x` and `projection_y` come back as `representation.numeric.decimal_number` — correct, and useless for that decision. Nothing in either descriptor says those two columns are a coordinate PAIR meant to be plotted against each other, so a surface that picks its chart from the descriptor sees two unrelated decimals and draws two histograms. A projection coordinate is a semantic kind finetype does not have, and these are the first two objects in this repository where its absence costs something.

**A label here is not stable across corpus size, and that is the sharper finding.** `medmcqa` was built first over the source's 4,183-row `validation` split and then over its 182,822-row `train` split — same Protocol, same source dataset, same `x-finetype-version` 0.6.57, same fifteen columns. **Two of the fifteen changed label, not merely confidence:**

| column | over 4,183 rows | over 182,822 rows |
|---|---|---|
| `subject_name` | `representation.text.word` (0.6306) | `representation.text.entity_name` (0.9615) |
| `projection_fit_id` | `unknown` (0.6721) | `representation.text.word` (0.9691) |

Six more moved in confidence alone, in both directions — `opc` fell from 0.9899 to 0.8881 while `topic_name` rose from 0.4598 to 0.9934. Reproduce it by changing the `url:` and `sha256:` in `medmcqa/arcform.yaml` to `data/validation-00000-of-00001.parquet` (sha256 `b768a1ea34afc9f80d3106d9b21f80fa8a00ec450a1f6cd641af72ca9e591021`) and re-running. So a semantic label in one of these descriptors is a reading of the values that were there, not a property of the column — which is worth knowing before anything downstream branches on one.

**Two more misses, both worse than the ones below.** `medmcqa.exp` — a worked medical explanation, several sentences of prose — types as `representation.identifier.alphanumeric_id` at confidence **1.0**, which is a wrong answer given with no hedge at all rather than a low-confidence guess. And `supergpqa.field`, whose values are things like "Electronic Science and Technology", types as `geography.location.city`. Every label in this section was read from the `x-finetype-label` in the committed `datapackage.json` files, the four for `movies`, `scienceqa`, `medmcqa` and `supergpqa` stamped `x-finetype-version` **0.6.57**, and the other seven, built later, **0.6.63**.

It is not uniformly right, and the miss is recorded here rather than quietly accepted: `census-income.final_weight` types as `identity.person.weight`. It is a Census *sampling* weight — how many people in the population the record stands for — and not a property of anybody's body. `scienceqa.grade` — a string like `grade5` — types as `finance.rate.basis_points`, which is a stranger miss than the census one and just as wrong: nothing about a school grade level resembles a rate.

**The five gallery recipes add four more misses, and one of them repeats.** `usgs-earthquakes-2025.magnitude_scale`, whose values are labels like "body wave (mb)", types as `finance.rate.basis_points`, the label `scienceqa.grade` got, so that miss is not a one-off. `epoch-ai-models.model`, a model's name, types as `representation.file.excel_format` at confidence 0.9991. `epoch-ai-models.access` and `.compute_record`, short category labels such as "open weights" and "recorded, confident", both type as `container.array.whitespace_separated`, at 0.9991 and 0.9971. What it gets right there is worth as much: the earthquakes' `latitude` and `longitude` come back as coordinates, so the USGS recipe is the second here whose map needs no embedding, and `online-retail-ii.country` types as `geography.location.country`.
